# Лекция 18. Хуки: useState, useEffect, useRef, useMemo, useCallback

**Цель лекции:** Освоить хуки — механизм, который даёт функциональному компоненту память и доступ к жизненному циклу. Понять правила вызова хуков и научиться использовать их в реальных задачах — таймер и поиск с debounce.

### **Детальное рассмотрение каждого пункта плана:**

#### **1. Что такое хуки и правила их вызова**

**Зачем компоненту память.**
Функциональный компонент — обычная функция, и при каждом рендере она вызывается заново. Обычные переменные, объявленные внутри, не сохраняются между вызовами:

```tsx
// Так НЕ работает: при каждом рендере count заново равен 0
export function BrokenCounter() {
  let count = 0;

  return (
    <button type="button" onClick={() => count++}>
      Нажато: {count}
    </button>
  );
}
```

Причина в том, что React вызывает функцию заново после каждого обновления, и локальная переменная создаётся с нуля. Чтобы компонент «помнил» данные между рендерами, нужен специальный механизм — **хуки** (hooks).

**Что такое хук.**
Хук — это функция React, имя которой начинается с `use` и которая даёт компоненту дополнительные возможности:

*   `useState` — хранить состояние между рендерами;
*   `useEffect` — выполнять побочные действия и очищать их;
*   `useRef` — обращаться к DOM и хранить значения без ререндера;
*   `useMemo` / `useCallback` — кэшировать вычисления и функции.

Хуки импортируются по отдельности из пакета `react`:

```tsx
import { useState, useEffect, useRef, useMemo, useCallback } from 'react';
```

Правило именования неслучайно: префикс `use` — подсказка и человеку, и линтеру, что перед ним хук со своими правилами вызова.

**Правило 1: только верхний уровень, до ранних `return`.**
Хуки нельзя вызывать внутри условий, циклов, вложенных функций, обработчиков событий и блоков `try/catch`. Все они должны стоять **в начале тела компонента**, до любого условного выхода:

```tsx
function Bad({ cond }) {
  if (cond) {
    // ❌ Нельзя: хук внутри условия
    const [x, setX] = useState(0);
  }

  // ❌ Нельзя: хук после раннего return
  if (!cond) {
    return null;
  }
  const [y, setY] = useState(0);
}
```

```tsx
function Good({ cond }) {
  // ✅ Правильно: все хуки — на верхнем уровне, до любых return
  const [x, setX] = useState(0);
  const [y, setY] = useState(0);

  if (!cond) {
    return null;
  }

  return <p>{x + y}</p>;
}
```

**Почему порядок вызова хуков критичен.**
React не может узнать хук «по имени»: он запоминает состояние компонента в том порядке, в котором хуки вызываются. Первый `useState` — слот № 1, второй — слот № 2, `useEffect` — слот № 3 и так далее.

Если хук вызывается условно, порядок между рендерами меняется, и React «сдвигает» состояние: значения попадают не в те слоты, а в консоли появляется ошибка:

```
React has detected a change in the order of Hooks called by Component.
Rendered more hooks than during the previous render.
```

Поэтому правило «только верхний уровень» — не стилистическое пожелание, а требование корректности. Условие при этом никуда не девается: оно переезжает **внутрь** хука или в его зависимости, а сам хук остаётся безусловным.

**Правило 2: только из компонентов и других хуков.**
Хук нельзя вызвать из обычной JavaScript-функции. Он работает только внутри рендера компонента (или другого хука, который тоже вызван из компонента):

```tsx
function FriendList() {
  // ✅ Правильно: хук вызывается внутри компонента
  const [online, setOnline] = useState(false);
}

function setOnlineStatus() {
  // ❌ Нельзя: это обычная функция, а не компонент и не хук
  const [online, setOnline] = useState(false);
}
```

Позже, в лекции 20, мы будем выносить логику в собственные хуки — функции с именем `useИмя`, которые вызываются из компонентов. Это законный способ переиспользовать поведение.

**Правило 3: линтер проверяет правила автоматически.**
Забыть про правила почти невозможно: в шаблоне Vite подключён линтер, который знает про хуки (правила `react-hooks/rules-of-hooks` и `react-hooks/exhaustive-deps` в ESLint; аналоги есть и в `oxlint`). Он:

*   подсвечивает хук внутри условия или после `return`;
*   подсказывает, какие значения добавить в массив зависимостей `useEffect`.

Соглашение об именах `use…` нужно линтеру, чтобы отличать хуки от обычных функций и проверять именно их.

> **Запомним:** хуки вызываются только на верхнем уровне компонента или другого хука, до ранних `return`, и всегда в одном и том же порядке.

#### **2. `useState` — состояние компонента**

**Синтаксис.**
`useState` принимает начальное значение и возвращает пару: текущее значение и функцию-сеттер.

```tsx
const [count, setCount] = useState(0);
```

Разберём:

*   `count` — текущее значение состояния на этом рендере;
*   `setCount` — функция, которая запрашивает у React обновление и **новый рендер**;
*   `0` — начальное значение, используется только при первом рендере.

Тип можно не указывать — TypeScript выведет его из начального значения. Но когда значение может быть, например, `null`, тип задают явно:

```tsx
const [user, setUser] = useState<User | null>(null);
```

**Начальное значение и ленивая инициализация.**
Начальное значение может быть не только литералом, но и результатом вычисления. Если вычисление дорогое (чтение из `localStorage`, разбор JSON, построение массива), его передают **функцией** — тогда оно выполнится один раз, при первом рендере:

```tsx
interface Settings {
  theme: 'light' | 'dark';
  fontSize: number;
}

function readSettings(): Settings {
  const saved = localStorage.getItem('settings');
  return saved ? (JSON.parse(saved) as Settings) : { theme: 'light', fontSize: 16 };
}

// ❌ Плохо: readSettings() вызовется на каждом рендере, а результат будет отброшен
const [settings, setSettings] = useState<Settings>(readSettings());

// ✅ Хорошо: колбэк вызовется только один раз — при монтировании
const [settings, setSettings] = useState<Settings>(() => readSettings());
```

Разница видна только в производительности, но правило простое: **результат дорогого вычисления — оборачивай в функцию**.

**Функциональное обновление.**
Сеттеру можно передать новое значение напрямую, а можно — функцию, которая получает предыдущее значение и возвращает следующее:

```tsx
const [count, setCount] = useState(0);

// Прямое значение
function reset() {
  setCount(0);
}

// Функциональное обновление: prev — гарантированно актуальное значение
function increment() {
  setCount((prev) => prev + 1);
}

function multiplyBy(factor: number) {
  setCount((prev) => prev * factor);
}
```

Функциональное обновление надёжнее везде, где новое значение зависит от предыдущего. Сравните:

```tsx
// ❌ Неверно: count берётся из замыкания текущего рендера, три раза одно и то же
function tripleWrong() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
  // результат: +1, а не +3
}

// ✅ Верно: каждое обновление получает свежее предыдущее значение
function tripleRight() {
  setCount((prev) => prev + 1);
  setCount((prev) => prev + 1);
  setCount((prev) => prev + 1);
  // результат: +3
}
```

**Иммутабельные обновления объектов и массивов.**
React определяет изменения по ссылке: если передать в сеттер **тот же самый** объект или массив, он может не увидеть изменений. Поэтому данные обновляют **иммутабельно** — создавая новую версию, а не изменяя старую.

```tsx
interface User {
  id: number;
  name: string;
  email: string;
}

const [user, setUser] = useState<User>({ id: 1, name: 'Иван', email: 'ivan@mail.ru' });

// ❌ Плохо: мутация — ссылка не изменилась, ререндера может не быть
function changeNameWrong() {
  user.name = 'Мария';
  setUser(user);
}

// ✅ Хорошо: копия с изменённым полем, остальные поля сохраняются через spread
function changeName() {
  setUser((prev) => ({ ...prev, name: 'Мария' }));
}
```

Массивы обновляются теми же неизменяющими методами, что мы разбирали в лекции 17:

```tsx
interface Todo {
  id: number;
  text: string;
  completed: boolean;
}

const [todos, setTodos] = useState<Todo[]>([]);

// Добавить элемент в конец — новый массив
setTodos((prev) => [...prev, { id: Date.now(), text: 'Новая задача', completed: false }]);

// Удалить по id — filter возвращает новый массив
setTodos((prev) => prev.filter((todo) => todo.id !== id));

// Изменить один элемент — map создаёт новый массив и новый объект
setTodos((prev) =>
  prev.map((todo) =>
    todo.id === id ? { ...todo, completed: !todo.completed } : todo,
  ),
);
```

> Правило: **никогда не мутируем state напрямую** — ни через присваивание полей, ни через `push`, `sort`, `splice`. Всегда создаём новую версию данных (`[...arr]`, `{ ...obj }`, `map`, `filter`). Этот же принцип мы применяли к props в лекции 17.

**Батчинг обновлений.**
Если в одном обработчике несколько раз вызвать сеттеры, React **сгруппирует** их в одно обновление и выполнит **один** ререндер — это называется батчингом (batching). Так было не всегда: до React 18 обновления внутри `async`-кода не группировались, а в React 19 автоматический батчинг работает всегда.

```tsx
const [count, setCount] = useState(0);
const [isOpen, setIsOpen] = useState(false);

function handleClick() {
  setCount((prev) => prev + 1);
  setIsOpen((prev) => !prev);
  // React увидит оба обновления и перерисует компонент один раз
}
```

**Состояние — это снимок.**
Важно понимать: `setCount` не меняет переменную `count` «на месте». React запоминает новое значение и рендерит компонент заново, а в **текущем** выполнении функции `count` остаётся прежним:

```tsx
function handleClick() {
  setCount(count + 1);
  console.log(count); // всё ещё старое значение!
}
```

Поэтому для расчётов на основе свежего значения и существует функциональная форма `setCount((prev) => …)`: она гарантирует, что `prev` — это актуальное состояние, а не устаревшее значение из замыкания.

**Несколько состояний против одного объекта.**
Небольшие независимые значения удобнее хранить в отдельных `useState`:

```tsx
const [name, setName] = useState('');
const [email, setEmail] = useState('');
const [isLoading, setIsLoading] = useState(false);
```

Так обновление одного поля не затрагивает остальные, а код читается проще. Один объект-состояние уместен, когда значения логически неразделимы:

```tsx
interface FormState {
  name: string;
  email: string;
}

const [form, setForm] = useState<FormState>({ name: '', email: '' });

function handleNameChange(value: string) {
  setForm((prev) => ({ ...prev, name: value }));
}
```

Если полей много и логика обновления однотипна, используют `useReducer`, но это тема отдельного разговора; для большинства задач `useState` достаточно.

**Контролируемые поля ввода.**
В React значение поля можно хранить в состоянии — тогда компонент полностью контролирует ввод. Это называется контролируемым компонентом (controlled component): значение приходит из `state`, а изменения уходят в сеттер через `onChange`.

```tsx
// src/components/NameForm.tsx
import { useState } from 'react';
import type { ChangeEvent } from 'react';

export function NameForm() {
  const [name, setName] = useState('');

  function handleChange(event: ChangeEvent<HTMLInputElement>) {
    setName(event.target.value);
  }

  const isValid = name.trim().length >= 2;

  return (
    <form onSubmit={(event) => event.preventDefault()}>
      <label htmlFor="name">Имя:</label>
      <input
        id="name"
        type="text"
        value={name}
        onChange={handleChange}
        placeholder="Введите имя"
      />

      {name.length > 0 && !isValid && (
        <p className="error">Имя должно содержать минимум 2 символа</p>
      )}

      <button type="submit" disabled={!isValid}>
        Сохранить
      </button>
    </form>
  );
}
```

Обратите внимание на `import type { ChangeEvent } from 'react'`: в шаблоне `react-ts` с параметром `verbatimModuleSyntax` типы импортируются отдельно от значений, иначе TypeScript выдаст ошибку сборки.

#### **3. `useEffect` — синхронизация с внешним миром**

**Что такое побочный эффект.**
Во время рендера компонент должен быть чистым: считать JSX из props и state, не трогая ничего снаружи (см. лекцию 16). Но приложению нужно взаимодействовать с внешним миром: отправлять запросы, подписываться на события, запускать таймеры, менять `document.title`. Такие действия называются **побочными эффектами**, и для них есть `useEffect`.

Важно сместить акцент восприятия: `useEffect` — это не «магия жизненного цикла», а **синхронизация состояния с внешней системой**. Формулируйте для себя так: «пока значения `a` и `b` такие — внешняя система должна выглядеть так».

**Синтаксис.**
`useEffect` принимает функцию-эффект и массив зависимостей. Из эффекта можно (и часто нужно) вернуть **cleanup-функцию** — код очистки:

```tsx
useEffect(() => {
  // 1. код, который выполняется после рендера
  //    (подключение, подписка, запрос, таймер)

  return () => {
    // 2. код очистки: вызывается перед следующим запуском
    //    и при размонтировании компонента
  };
}, [deps]);
```

**Массив зависимостей.**
От второго аргумента зависит, когда эффект запускается:

```tsx
// Запускается после КАЖДОГО рендера (массива нет)
useEffect(() => {
  console.log('рендер завершён');
});

// Запускается один раз — при монтировании (в dev-режиме StrictMode — дважды, см. ниже)
useEffect(() => {
  console.log('компонент появился');
}, []);

// Запускается при монтировании и каждый раз,
// когда изменилось a или b
useEffect(() => {
  console.log('a или b изменились');
}, [a, b]);
```

Сводка:

| Второй аргумент | Когда запускается эффект | Типичный случай |
| :--- | :--- | :--- |
| отсутствует | после каждого рендера | нужно синхронизировать почти всё; использовать редко |
| `[]` | только при монтировании (и cleanup — при размонтировании) | подписка на событие окна, загрузка данных |
| `[a, b]` | при монтировании и при изменении `a` или `b` | таймер, зависящий от `isRunning`; запрос по `query` |

**Cleanup: таймеры, подписки, события.**
Если эффект что-то «включил», cleanup обязан это «выключить». Иначе получим утечки, дублирующиеся таймеры и «фантомные» обработчики.

```tsx
// ✅ Таймер с корректной очисткой
useEffect(() => {
  const id = window.setInterval(() => {
    setSeconds((prev) => prev + 1);
  }, 1000);

  return () => window.clearInterval(id);
}, []);
```

Частая ошибка — забыть cleanup:

```tsx
// ❌ Плохо: интервал никогда не очищается.
// В StrictMode dev-режима эффект запустится дважды — и счётчик будет «тикать» вдвое быстрее
useEffect(() => {
  window.setInterval(() => {
    setSeconds((prev) => prev + 1);
  }, 1000);
}, []);
```

Подписка на событие окна — тот же принцип: добавили обработчик — удалите его в cleanup.

```tsx
// src/hooks/useWindowWidth.ts — пример по смыслу; как оформить свой хук, см. лекцию 20
import { useEffect, useState } from 'react';

export function useWindowWidth(): number {
  const [width, setWidth] = useState(() => window.innerWidth);

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth);
    }

    window.addEventListener('resize', handleResize);

    // cleanup: иначе обработчики будут накапливаться при каждом монтировании
    return () => window.removeEventListener('resize', handleResize);
  }, []);

  return width;
}
```

Обратите внимание: в cleanup передаётся **та же самая ссылка** на функцию `handleResize`, поэтому её объявляют внутри эффекта.

**Загрузка данных при монтировании; защита от гонок.**
Самый частый сценарий — получить данные с сервера, когда компонент появился. Здесь важно предусмотреть две вещи: отмену запроса при размонтировании и защиту от «гонок», когда ответы приходят не в том порядке.

```tsx
// src/components/UserList.tsx
import { useEffect, useState } from 'react';

interface User {
  id: number;
  name: string;
}

export function UserList() {
  const [users, setUsers] = useState<User[]>([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    // AbortController позволяет отменить fetch при размонтировании
    const controller = new AbortController();

    async function loadUsers() {
      setIsLoading(true);
      setError(null);

      try {
        const response = await fetch('/api/users', { signal: controller.signal });

        if (!response.ok) {
          throw new Error(`Сервер ответил ошибкой ${response.status}`);
        }

        const data: User[] = await response.json();
        setUsers(data);
      } catch (err) {
        // Отменённый запрос — это не ошибка, просто игнорируем
        if (err instanceof DOMException && err.name === 'AbortError') {
          return;
        }

        setError(err instanceof Error ? err.message : 'Не удалось загрузить данные');
      } finally {
        if (!controller.signal.aborted) {
          setIsLoading(false);
        }
      }
    }

    void loadUsers();

    // cleanup: отменяем запрос, если компонент размонтировали
    return () => controller.abort();
  }, []);

  if (isLoading) {
    return <p role="status">Загрузка...</p>;
  }

  if (error) {
    return (
      <p className="error" role="alert">
        {error}
      </p>
    );
  }

  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

Если тот же эффект зависит от параметра (например, `userId`), добавьте его в зависимости — и cleanup с `AbortController` автоматически отменит устаревший запрос:

```tsx
useEffect(() => {
  // ...запрос данных для userId
}, [userId]);
```

Так мы получаем защиту от гонок: запрос для старого `userId` отменяется, и его ответ не сможет перезаписать актуальные данные.

**Двойной вызов эффектов в `StrictMode` в dev-режиме.**
В `main.tsx` приложение обёрнуто в `<StrictMode>` (лекция 15). В dev-режиме React намеренно монтирует компонент, размонтирует и монтирует снова — чтобы найти эффекты без корректного cleanup. Поэтому каждый эффект в режиме разработки выполняется дважды.

Это не баг: в production-сборке двойного вызова нет. Но это отличный индикатор качества кода:

*   если эффект запустил таймер и **не очистил** его — счётчик будет идти вдвое быстрее;
*   если подписка не снимается — обработчик сработает дважды;
*   если эффект корректно очищается — двойной запуск безвреден.

Именно поэтому cleanup обязателен для любого эффекта, который что-то подключает.

**Ловушка бесконечного цикла.**
Эффект с зависимостью, которая меняется на каждом рендере, превращается в бесконечный цикл:

```tsx
// ❌ Плохо: объект options создаётся заново каждый рендер —
// ссылка всегда новая, эффект запускается бесконечно
const options = { page: 1, limit: 10 };

useEffect(() => {
  loadData(options);
}, [options]);
```

То же случается, если внутри эффекта обновлять состояние, которое есть в его зависимостях:

```tsx
// ❌ Плохо: setCount меняет count → эффект запускается снова → бесконечный цикл
useEffect(() => {
  setCount(count + 1);
}, [count]);
```

Лечится это так: объект либо создаётся внутри эффекта, либо стабилизируется через `useMemo`; а состояние внутри эффекта обновляют функционально и не указывают как зависимость, если эффект не должен реагировать на его изменение.

**Когда `useEffect` не нужен.**
`useEffect` часто применяют там, где он не требуется. Два правила помогут избежать лишних эффектов.

1.  **Производные данные вычисляют при рендере, а не в эффекте.**

```tsx
// ❌ Лишний эффект: значение можно посчитать сразу
const [fullName, setFullName] = useState('');
useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);

// ✅ Просто вычисление при рендере
const fullName = `${firstName} ${lastName}`;
```

2.  **Реакцию на действие пользователя делают в обработчике, а не в эффекте.**

```tsx
// ❌ Лишний эффект: покупка выполняется из-за изменения состояния
useEffect(() => {
  if (product) {
    post('/api/buy', product);
  }
}, [product]);

// ✅ Действие выполняется прямо в обработчике события
function handleBuy() {
  post('/api/buy', product);
}
```

Эффект нужен тогда, когда действие должно произойти **из-за того, что компонент отображён с определёнными данными**, а не из-за конкретного клика.

#### **4. `useRef` — DOM и значения без ререндера**

**Два разных применения одного хука.**
`useRef` возвращает объект с единственным свойством `current`, который сохраняется между рендерами. И у него две принципиально разные роли:

1.  **ссылка на DOM-узел** — чтобы напрямую вызвать метод элемента (фокус, прокрутка, измерение);
2.  **«коробочка» для значения**, изменение которого **не должно** вызывать ререндер.

```tsx
const ref = useRef<HTMLInputElement>(null);
// ref.current — либо DOM-узел, либо null до монтирования
```

Ключевое отличие от `useState`: **изменение `ref.current` не запускает рендер**. Именно поэтому `useRef` хорош для служебных значений, которые не отображаются в разметке.

**Доступ к DOM-узлу: фокус на поле ввода.**
Чтобы получить DOM-элемент, нужно создать ref и передать его в атрибут `ref`:

```tsx
// src/components/SearchForm.tsx
import { useRef } from 'react';

export function SearchForm() {
  const inputRef = useRef<HTMLInputElement>(null);

  function focusInput() {
    // current может быть null, если компонент ещё не смонтирован
    inputRef.current?.focus();
  }

  return (
    <form onSubmit={(event) => event.preventDefault()}>
      <label htmlFor="search">Поиск:</label>
      <input id="search" ref={inputRef} type="text" placeholder="Введите запрос" />

      <button type="button" onClick={focusInput}>
        Перейти к поиску
      </button>
    </form>
  );
}
```

Разберём:

*   типовой параметр `useRef<HTMLInputElement>` говорит TypeScript, что в `current` будет элемент `<input>`;
*   начальное значение `null` — до монтирования DOM-узла не существует;
*   `inputRef.current?.focus()` — безопасный вызов: если узел ещё не создан, ничего не произойдёт;
*   атрибут `ref` — обычный prop; React сам записывает в него DOM-узел после отрисовки.

Автофокус при появлении формы — частный случай, но его можно решить эффектом:

```tsx
import { useEffect, useRef } from 'react';

export function AutoFocusInput() {
  const inputRef = useRef<HTMLInputElement>(null);

  useEffect(() => {
    inputRef.current?.focus();
  }, []); // при монтировании

  return <input ref={inputRef} type="text" aria-label="Поиск по каталогу" />;
}
```

**Измерение элемента после отрисовки.**
Доступ к DOM нужен, когда размеры или позицию элемента можно узнать только у реального браузерного узла. Измеряем внутри `useEffect` — к этому моменту DOM уже построен:

```tsx
import { useEffect, useRef, useState } from 'react';

export function WidthMeter() {
  const boxRef = useRef<HTMLDivElement>(null);
  const [width, setWidth] = useState(0);

  useEffect(() => {
    if (boxRef.current) {
      setWidth(boxRef.current.getBoundingClientRect().width);
    }
  }, []);

  return (
    <div ref={boxRef} className="meter">
      Ширина блока: {Math.round(width)} px
    </div>
  );
}
```

**Хранение значения без ререндера (id таймера, предыдущее значение).**
Самое практичное применение — хранить служебные данные, которые не участвуют в разметке. Классический пример — идентификатор таймера при ручном управлении:

```tsx
import { useRef, useState } from 'react';

export function ManualTimer() {
  const [seconds, setSeconds] = useState(0);
  const intervalRef = useRef<number | null>(null);

  function start() {
    // Защита от двойного запуска
    if (intervalRef.current !== null) {
      return;
    }

    intervalRef.current = window.setInterval(() => {
      setSeconds((prev) => prev + 1);
    }, 1000);
  }

  function stop() {
    if (intervalRef.current !== null) {
      window.clearInterval(intervalRef.current);
      intervalRef.current = null;
    }
  }

  return (
    <div>
      <p>Прошло секунд: {seconds}</p>
      <button type="button" onClick={start}>
        Старт
      </button>
      <button type="button" onClick={stop}>
        Стоп
      </button>
    </div>
  );
}
```

Почему здесь именно `useRef`, а не `useState`: идентификатор интервала нигде не выводится, и его изменение не должно перерисовывать компонент. Если бы это был `useState`, каждое присваивание вызывало бы лишний ререндер.

Второй типичный сценарий — запомнить значение с **предыдущего** рендера:

```tsx
import { useEffect, useRef, useState } from 'react';

export function CounterWithHistory() {
  const [count, setCount] = useState(0);
  const prevCountRef = useRef(0);

  useEffect(() => {
    prevCountRef.current = count;
  }, [count]);

  return (
    <div>
      <p>Сейчас: {count}</p>
      <p>Было: {prevCountRef.current}</p>
      <button type="button" onClick={() => setCount((prev) => prev + 1)}>
        Увеличить
      </button>
    </div>
  );
}
```

**Чем `useRef` отличается от `useState`.**

| | `useState` | `useRef` |
| :--- | :--- | :--- |
| Значение живёт между рендерами | да | да |
| Изменение вызывает ререндер | да | **нет** |
| Для чего | данные, отображаемые в UI | DOM-узлы, служебные значения, id таймеров |
| Чтение | значение напрямую | через `ref.current` |
| Изменение | только через сеттер | напрямую (`ref.current = …`) |

> Правило выбора: если значение влияет на то, что видит пользователь, — это `useState`. Если это «техническая» переменная (ссылка на DOM, id таймера, счётчик попыток), — `useRef`.

#### **5. `useMemo` и `useCallback` — мемоизация**

**Что такое мемоизация.**
Мемоизация — это кэширование результата: если входные данные не изменились, повторно вычислять не нужно, можно вернуть сохранённый результат. React сравнивает зависимости поверхностно (по ссылке для объектов и функций) и пересчитывает значение только тогда, когда хотя бы одна зависимость изменилась.

**`useMemo`: кэш результата вычисления.**

```tsx
const memoizedValue = useMemo(() => computeExpensiveValue(a, b), [a, b]);
```

Функция из первого аргумента выполнится при первом рендере и будет пересчитана только при изменении `a` или `b`. Во все остальные рендеры React вернёт закэшированный результат.

Типичный случай — фильтрация и сортировка большого списка:

```tsx
// src/components/ProductList.tsx
import { useMemo, useState } from 'react';

interface Product {
  id: number;
  title: string;
  price: number;
  category: string;
}

interface ProductListProps {
  products: Product[];
  category: string;
}

export function ProductList({ products, category }: ProductListProps) {
  const [onlyAffordable, setOnlyAffordable] = useState(false);

  const visibleProducts = useMemo(() => {
    const filtered = products.filter((product) =>
      category === 'all' ? true : product.category === category,
    );

    const byPrice = onlyAffordable
      ? filtered.filter((product) => product.price <= 50000)
      : filtered;

    // сортируем копию, не мутируя props
    return [...byPrice].sort((a, b) => a.price - b.price);
  }, [products, category, onlyAffordable]);

  return (
    <div>
      <label>
        <input
          type="checkbox"
          checked={onlyAffordable}
          onChange={(event) => setOnlyAffordable(event.target.checked)}
        />
        Только до 50 000 ₽
      </label>

      <p>Найдено товаров: {visibleProducts.length}</p>

      <ul>
        {visibleProducts.map((product) => (
          <li key={product.id}>
            {product.title} — {product.price} ₽
          </li>
        ))}
      </ul>
    </div>
  );
}
```

Важно: `useMemo` не «ускоряет всё подряд» — он лишь избавляет от повторного вычисления. Если пересчёт дешёвый (сложение двух чисел, короткий массив из пяти элементов), выгоды нет, а код усложняется.

**`useCallback`: стабильная ссылка на функцию.**

```tsx
const memoizedCallback = useCallback(() => {
  doSomething(a, b);
}, [a, b]);
```

`useCallback` возвращает **ту же самую** функцию между рендерами, пока не изменились зависимости. Зачем это нужно:

*   функция передаётся в дочерний компонент, обёрнутый в `memo` — без стабильной ссылки дочерний компонент будет перерисовываться зря;
*   функция является зависимостью `useEffect` — без стабильной ссылки эффект будет запускаться на каждом рендере;
*   значение помещается в контекст или используется в `useMemo`.

```tsx
import { memo, useCallback, useState } from 'react';

interface TodoItemProps {
  id: number;
  title: string;
  onDelete: (id: number) => void;
}

// memo пропускает ререндер, если props не изменились
const TodoItem = memo(function TodoItem({ id, title, onDelete }: TodoItemProps) {
  return (
    <li>
      {title}
      <button type="button" onClick={() => onDelete(id)}>
        Удалить
      </button>
    </li>
  );
});

export function TodoList() {
  const [todos, setTodos] = useState([{ id: 1, title: 'Изучить хуки' }]);

  // Стабильная ссылка: дочерние memo-компоненты не перерисуются зря
  const handleDelete = useCallback((id: number) => {
    setTodos((prev) => prev.filter((todo) => todo.id !== id));
  }, []);

  return (
    <ul>
      {todos.map((todo) => (
        <TodoItem key={todo.id} id={todo.id} title={todo.title} onDelete={handleDelete} />
      ))}
    </ul>
  );
}
```

`memo` — не хук, а функция-обёртка: она импортируется из `react` вместе с хуками и пропускает ререндер, если props не изменились.

**Связь между хуками.**
`useCallback` — это частный случай `useMemo` для функций:

```tsx
// Эти записи эквивалентны
const handleClick = useCallback(() => doSomething(a), [a]);
const handleClick = useMemo(() => () => doSomething(a), [a]);
```

Поэтому не нужно применять оба хука к одному и тому же: для функции — `useCallback`, для значения — `useMemo`.

**Когда мемоизация действительно нужна.**

*   Вычисление действительно тяжёлое: большие массивы, сложные расчёты, агрегация, форматирование тысяч строк.
*   Ссылка должна быть стабильной: `memo`-компонент, зависимость `useEffect`, значение контекста.
*   Проблему видно в профилировщике React DevTools (Profiler): рендеры повторяются без причины.

**Преждевременная оптимизация.**
Мемоизация не бесплатна: каждый `useMemo` и `useCallback` занимает память и добавляет сравнение зависимостей на каждом рендере. Если обернуть во всё подряд, код станет сложнее, а выигрыша не будет — иногда приложение даже замедлится.

```tsx
// ❌ Преждевременная оптимизация: сложение — операция на наносекунды,
// кэшировать её бессмысленно
const sum = useMemo(() => a + b, [a, b]);

// ✅ Мемоизация оправдана: пересчёт большого массива
const totals = useMemo(
  () => orders.reduce((acc, order) => acc + order.amount, 0),
  [orders],
);
```

Практическое правило: **сначала пишем просто и ясно, измеряем производительность, и только потом добавляем мемоизацию там, где она реально помогает**. Большинство компонентов в `useMemo` и `useCallback` не нуждаются.

#### **6. Сводная таблица «Задача → хук»**

| Задача | Хук | Пример |
| :--- | :--- | :--- |
| Хранить данные компонента и обновлять UI | `useState` | счётчик, поле формы, флаг открытия |
| Обновить состояние на основе предыдущего | `useState` с функцией | `setCount((prev) => prev + 1)` |
| Хранить объект/массив и менять иммутабельно | `useState` + spread/`map`/`filter` | `setUser((prev) => ({ ...prev, name }))` |
| Реагировать на изменение данных после рендера | `useEffect` + зависимости | запрос при смене `query` |
| Выполнить действие один раз при монтировании | `useEffect` с `[]` | первоначальная загрузка данных |
| Подписаться на событие или завести таймер | `useEffect` + cleanup | `setInterval` / `addEventListener` |
| Отменить запрос или подписку | cleanup в `useEffect` | `AbortController.abort()` |
| Получить доступ к DOM-узлу | `useRef` | фокус на `input`, измерение блока |
| Хранить значение, не влияющее на UI | `useRef` | id таймера, предыдущее значение |
| Кэшировать тяжёлое вычисление | `useMemo` | фильтрация и сортировка большого списка |
| Стабилизировать ссылку на функцию | `useCallback` | обработчик для `memo`-компонента |

Дополнение: `useReducer` подходит для сложной логики обновления состояния, `useContext` — для передачи данных через дерево компонентов, `useId` — для связки `label` и поля ввода. Эти хуки разбираются в лекциях 19 и 23.

#### **7. Практика: таймер и поиск с debounce**

Соберём приложение из двух блоков: **таймер** с пуском, паузой и сбросом и **поиск** с задержкой (debounce), чтобы запрос уходил не на каждое нажатие клавиши, а после паузы.

**Шаг 1. Компонент `Timer`.**
Здесь задействуем `useState` (значение и флаг работы), `useEffect` (интервал + cleanup, зависящий от флага) и `useCallback` (стабильные обработчики).

```tsx
// src/components/Timer.tsx
import { useCallback, useEffect, useState } from 'react';

function formatTime(totalSeconds: number): string {
  const minutes = Math.floor(totalSeconds / 60);
  const seconds = totalSeconds % 60;
  return `${String(minutes).padStart(2, '0')}:${String(seconds).padStart(2, '0')}`;
}

export function Timer() {
  const [seconds, setSeconds] = useState(0);
  const [isRunning, setIsRunning] = useState(false);

  // Эффект запускает интервал только когда таймер идёт.
  // cleanup останавливает интервал при паузе и при размонтировании.
  useEffect(() => {
    if (!isRunning) {
      return;
    }

    const id = window.setInterval(() => {
      setSeconds((prev) => prev + 1);
    }, 1000);

    return () => window.clearInterval(id);
  }, [isRunning]);

  const handleToggle = useCallback(() => {
    setIsRunning((prev) => !prev);
  }, []);

  const handleReset = useCallback(() => {
    setIsRunning(false);
    setSeconds(0);
  }, []);

  return (
    <section className="timer">
      <h2>Таймер</h2>
      <p className="timer__display" aria-live="polite">
        {formatTime(seconds)}
      </p>

      <div className="timer__controls">
        <button type="button" onClick={handleToggle}>
          {isRunning ? 'Пауза' : 'Старт'}
        </button>
        <button type="button" onClick={handleReset} disabled={seconds === 0}>
          Сброс
        </button>
      </div>
    </section>
  );
}
```

Что здесь важно:

*   эффект **зависит от `isRunning`**: при `true` интервал создаётся, при `false` — cleanup его снимает;
*   `setSeconds((prev) => prev + 1)` — функциональное обновление, потому что интервальный колбэк «не знает» о текущем `seconds`;
*   `handleReset` сначала останавливает таймер (`setIsRunning(false)`), затем обнуляет значение;
*   `aria-live="polite"` сообщает скринридеру об обновлении времени.

**Шаг 2. Компонент `UserSearch` с debounce.**
Задержка реализуется через `setTimeout` внутри `useEffect`: пока пользователь печатает, предыдущий таймер отменяется в cleanup, и новый запрос уйдёт только после паузы.

```tsx
// src/components/UserSearch.tsx
import { useEffect, useState } from 'react';

interface User {
  id: number;
  name: string;
  email: string;
}

const DEBOUNCE_DELAY = 500;

export function UserSearch() {
  const [query, setQuery] = useState('');
  const [users, setUsers] = useState<User[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const trimmed = query.trim();

    // Пустой запрос: не обращаемся к серверу, сразу показываем подсказку
    if (trimmed === '') {
      setUsers([]);
      setError(null);
      setIsLoading(false);
      return;
    }

    setIsLoading(true);
    setError(null);

    const controller = new AbortController();

    // Таймер задержки: если пользователь продолжит печатать,
    // cleanup отменит этот таймер и запустит новый
    const timeoutId = window.setTimeout(() => {
      void (async () => {
        try {
          const response = await fetch(
            `/api/users?search=${encodeURIComponent(trimmed)}`,
            { signal: controller.signal },
          );

          if (!response.ok) {
            throw new Error(`Сервер ответил ошибкой ${response.status}`);
          }

          const data: User[] = await response.json();
          setUsers(data);
          setIsLoading(false);
        } catch (err) {
          if (err instanceof DOMException && err.name === 'AbortError') {
            return;
          }

          setError(err instanceof Error ? err.message : 'Не удалось выполнить поиск');
          setIsLoading(false);
        }
      })();
    }, DEBOUNCE_DELAY);

    // cleanup: снимаем таймер и отменяем незавершённый запрос
    return () => {
      window.clearTimeout(timeoutId);
      controller.abort();
    };
  }, [query]);

  return (
    <section className="search">
      <h2>Поиск пользователей</h2>

      <label htmlFor="user-search">Запрос:</label>
      <input
        id="user-search"
        type="search"
        value={query}
        onChange={(event) => setQuery(event.target.value)}
        placeholder="Начните вводить имя"
      />

      {isLoading && (
        <p className="search__status" role="status">
          Поиск...
        </p>
      )}

      {error && (
        <p className="search__error" role="alert">
          {error}
        </p>
      )}

      {!isLoading && !error && query.trim() !== '' && users.length === 0 && (
        <p className="search__empty">Ничего не найдено</p>
      )}

      <ul className="search__results">
        {users.map((user) => (
          <li key={user.id}>
            <strong>{user.name}</strong> — {user.email}
          </li>
        ))}
      </ul>
    </section>
  );
}
```

Как работает debounce:

1.  пользователь нажал клавишу → `query` изменился;
2.  React запускает эффект, который ставит `setTimeout` на 500 мс;
3.  пользователь нажал следующую клавишу до истечения таймера → cleanup **снимает** предыдущий `setTimeout` и `abort`-ит предыдущий запрос;
4.  когда пауза достигла 500 мс, выполняется последний таймер и уходит один запрос.

Итог: при быстром вводе запрос отправляется один раз — после того, как пользователь остановился. Это и есть debounce; он строится ровно на `useEffect` + `setTimeout` с cleanup.

### **Резюме**

*   **Хуки** дают функциональному компоненту память и доступ к побочным действиям. Вызываются **только на верхнем уровне** компонента или другого хука, **до ранних `return`**, и всегда в одном и том же порядке.
*   **Порядок вызова хуков** критичен: React сопоставляет состояние со слотами по порядку, поэтому хук внутри условия или цикла ломает компонент.
*   **`useState`** хранит состояние между рендерами:
    *   начальное значение можно передать функцией — это **ленивая инициализация** для дорогих вычислений;
    *   обновление зависит от предыдущего значения — используем функцию: `setCount((prev) => prev + 1)`;
    *   объекты и массивы обновляются **иммутабельно**: `{ ...prev, поле }`, `map`, `filter`;
    *   несколько `setState` в одном обработчике батчатся в **один** ререндер;
    *   состояние — это **снимок**: в текущем рендере переменная остаётся прежней.
*   **`useEffect`** синхронизирует компонент с внешним миром:
    *   без массива зависимостей — после каждого рендера, `[]` — при монтировании, `[a, b]` — при изменении `a` или `b`;
    *   cleanup-функция снимает таймеры, подписки и отменяет запросы;
    *   загрузка данных при монтировании сопровождается `AbortController` — для отмены и защиты от гонок;
    *   в `StrictMode` dev-режима эффекты выполняются дважды — это проверка корректности cleanup, в production двойного вызова нет;
    *   производные данные и реакции на действия пользователя в `useEffect` **не нужны**.
*   **`useRef`** хранит объект, который живёт между рендерами, но **не вызывает ререндер**:
    *   ссылка на DOM-узел (`ref.current?.focus()`, измерение через `getBoundingClientRect`);
    *   служебные значения: id таймера, предыдущее значение, флаг первого рендера.
*   **`useMemo`** кэширует результат вычисления, **`useCallback`** — ссылку на функцию. Они нужны для дорогих расчётов и стабилизации ссылок (для `memo`-компонентов и зависимостей эффектов), но **преждевременная оптимизация вредна**: сначала измеряем, потом оптимизируем.
*   **Выбор хука:** влияет на UI → `useState`; действие после рендера → `useEffect`; доступ к DOM или служебное значение → `useRef`; кэш вычисления → `useMemo`; стабильная функция → `useCallback`.
*   Порядок работы с эффектом: **определить внешнюю систему → указать зависимости → обязательно написать cleanup**.
