### **Детальное рассмотрение каждого пункта плана:**

#### **1. Введение: логика прямо в JSX**

**Почему в React нет шаблонного языка.**
В шаблонных движках для условий и циклов обычно есть собственный синтаксис: специальные конструкции, служебные атрибуты, списки переменных контекста. В React этого нет. JSX — это JavaScript, поэтому условия и переборы коллекций записываются **обычными средствами языка**: `if`, тернарный оператор, `&&`, `switch`, `map`.

Единственное ограничение: внутри фигурных скобок `{ }` в разметке допустимо только **выражение**, а не инструкция. Поэтому `if` и `for` нельзя написать прямо внутри JSX — их выносят в тело функции до `return` или в отдельную функцию-помощник.

```tsx
// Так нельзя: `if` — это инструкция, а не выражение
// return <div>{if (isLoading) { <Spinner /> }}</div>;

// Так можно: значение заранее вычислено обычным JavaScript
function Status({ isLoading }: { isLoading: boolean }) {
  if (isLoading) {
    return <p>Загрузка...</p>;
  }

  return <p>Данные получены</p>;
}
```

Главное правило этой лекции: **сначала вычисляем — потом рендерим**. Любую сложную логику (условия, фильтры, сортировку) выполняем до `return` в теле компонента, а в JSX оставляем только подстановку готового результата. Тогда разметка остаётся короткой и читаемой.

#### **2. Условный рендеринг**

**`if` / `else` до `return`.**
Самый простой и самый читаемый способ — не рендерить условие внутри разметки, а выбрать, какую разметку вернуть. Ветвление происходит в обычном JavaScript-коде компонента:

```tsx
// src/components/LoginButton.tsx
interface LoginButtonProps {
  isLoggedIn: boolean;
  userName: string;
}

export function LoginButton({ isLoggedIn, userName }: LoginButtonProps) {
  if (isLoggedIn) {
    return (
      <div className="user-menu">
        <span>Привет, {userName}!</span>
        <button type="button">Выйти</button>
      </div>
    );
  }

  return <button type="button">Войти</button>;
}
```

Читается так же, как обычная функция: сначала проверяем условие, потом возвращаем результат. Такой подход хорош, когда вариантов два-три и они описывают **разные состояния всего компонента**.

**Ранний выход (early return).**
Отдельная полезная привычка — «отсекать» невозможные случаи в начале функции и не вкладывать условия друг в друга:

```tsx
interface ProfileProps {
  user: { name: string; email: string } | null;
}

export function Profile({ user }: ProfileProps) {
  // Ранний выход: дальше код выполняется только с реальным пользователем
  if (!user) {
    return <p className="muted">Пользователь не выбран</p>;
  }

  return (
    <article className="profile">
      <h2>{user.name}</h2>
      <a href={`mailto:${user.email}`}>{user.email}</a>
    </article>
  );
}
```

Глубокая вложенность `if` внутри `if` — верный признак, что логику пора переписать через ранние выходы или вынести в отдельный компонент.

**Возврат `null` — «ничего не рендерить».**
Компонент имеет право вернуть `null`. Это не ошибка: React просто не создаст для него ни одного DOM-узла. Так удобно реализовывать необязательные элементы — подсказки, бейджи, всплывающие блоки:

```tsx
// src/components/UserBadge.tsx
interface UserBadgeProps {
  user: { name: string; isAdmin: boolean } | null;
}

export function UserBadge({ user }: UserBadgeProps) {
  // Нет пользователя или он не администратор — элемента в DOM не будет
  if (!user || !user.isAdmin) {
    return null;
  }

  return <span className="badge badge--admin">Администратор</span>;
}
```

Важно: `null`, `undefined`, `false` и `true` React **не выводит на экран**. Это отличает их от `0` — о нём ниже.

**Тернарный оператор — выбор одного из двух.**
Когда оба варианта должны находиться в одном месте разметки (например, внутри `<footer>`), используют тернарный оператор:

```tsx
// src/components/ProductCard.tsx
interface ProductCardProps {
  title: string;
  price: number;
  inStock: boolean;
}

export function ProductCard({ title, price, inStock }: ProductCardProps) {
  return (
    <article className="product-card">
      <h3>{title}</h3>
      <p className="price">{price} ₽</p>

      {inStock ? (
        <span className="stock stock--available">В наличии</span>
      ) : (
        <span className="stock stock--unavailable">Нет в наличии</span>
      )}
    </article>
  );
}
```

Правила хорошего тона:

*   тернарный оператор — **только для двух** вариантов;
*   не вкладывать тернарник в тернарник — читаемость падает катастрофически;
*   если вариантов три и больше — выносим логику в переменную, функцию или `switch` (см. ниже).

```tsx
// Плохо: вложенные тернарные операторы
{role === 'admin' ? <AdminPanel /> : role === 'teacher' ? <TeacherPanel /> : <GuestPanel />}

// Хорошо: отдельная функция возвращает готовый JSX
function renderPanel(role: Role) {
  if (role === 'admin') {
    return <AdminPanel />;
  }

  if (role === 'teacher') {
    return <TeacherPanel />;
  }

  return <GuestPanel />;
}

// в разметке остаётся одно короткое выражение
{renderPanel(role)}
```

**Оператор `&&` и ловушка ложных значений.**
Самый компактный способ «показать, если истина» — логическое И:

```tsx
{isLoading && <p>Загрузка...</p>}
{hasError && <p className="error">Не удалось загрузить данные</p>}
{isNew && <span className="badge">Новинка</span>}
```

Работает это так: если левый операнд **falsy** (`false`, `null`, `undefined`, `0`, `''`, `NaN`) — React ничего не рендерит; если **truthy** — рендерит правый операнд.

И вот главная ловушка: число `0` — falsy-значение, но React выведет его на экран как текст. Это самая частая ошибка начинающих:

```tsx
// ЛОВУШКА: при пустом массиве на экране появится «0»
{tasks.length && <p>Задач: {tasks.length}</p>}

// Что произойдёт:
// tasks.length = 3 → «Задач: 3»
// tasks.length = 0 → «0»     (!) левый операнд равен 0, а React 0 показывает
```

То же касается `NaN`. Пустая строка `''` тоже falsy, но, в отличие от нуля, она создаёт пустой текстовый узел — визуально это не заметно, однако в некоторых случаях (например, при верстке через `:empty` или при отступах `gap`) лишний узел может непредсказуемо повлиять на расположение элементов, поэтому и её лучше не оставлять.

Решение простое: **слева от `&&` всегда должно стоять булево выражение**.

```tsx
// Правильно: сравнение возвращает boolean
{tasks.length > 0 && <p>Задач: {tasks.length}</p>}

// Альтернативы
{Boolean(query) && <p>Результаты по запросу «{query}»</p>}
{items.length !== 0 && <span className="badge">{items.length}</span>}
{!!user && <UserMenu user={user} />}
```

Если значение может быть `0` и должно отображаться именно как `0` — это нормально, но тогда его нельзя использовать в качестве условия. Разделяем: условие — булево, содержимое — значение.

```tsx
// Надёжный шаблон: условие булево, а сам ноль показываем осознанно
{count !== null && <p>Найдено записей: {count}</p>}
```

**Несколько вариантов: `switch` и словарь-справочник.**
Когда вариантов много, самый читаемый инструмент — `switch` внутри функции или отдельного компонента:

```tsx
// src/components/Alert.tsx
type AlertLevel = 'info' | 'success' | 'warning' | 'error';

interface AlertProps {
  level: AlertLevel;
  message: string;
}

function getAlertClass(level: AlertLevel): string {
  switch (level) {
    case 'info':
      return 'alert alert--info';
    case 'success':
      return 'alert alert--success';
    case 'warning':
      return 'alert alert--warning';
    case 'error':
      return 'alert alert--error';
    default:
      return 'alert';
  }
}

export function Alert({ level, message }: AlertProps) {
  return <div className={getAlertClass(level)}>{message}</div>;
}
```

Если варианты отличаются не оформлением, а разметкой, `switch` возвращает JSX:

```tsx
function NotificationBody({ level, message }: AlertProps) {
  switch (level) {
    case 'success':
      return <p className="alert__text">Операция выполнена: {message}</p>;
    case 'warning':
      return <p className="alert__text">Внимание: {message}</p>;
    case 'error':
      return <p className="alert__text">Ошибка: {message}</p>;
    default:
      return <p className="alert__text">{message}</p>;
  }
}
```

Для простых текстовых подписей ещё компактнее использовать словарь — обычный объект с `Record`:

```tsx
type Status = 'active' | 'blocked' | 'pending';

const STATUS_LABELS: Record<Status, string> = {
  active: 'Активен',
  blocked: 'Заблокирован',
  pending: 'Ожидает проверки',
};

export function UserStatus({ status }: { status: Status }) {
  return <span className={`status status--${status}`}>{STATUS_LABELS[status]}</span>;
}
```

Здесь важное преимущество TypeScript: `Record<Status, string>` не позволит забыть ни один вариант, и при добавлении нового статуса компилятор сразу покажет, где нужно дополнить словарь.

**Что React не выводит на экран.**
Полезно запомнить таблицу значений, которые безопасно возвращать из компонента или использовать в условии:

| Значение | Что увидит пользователь |
| :--- | :--- |
| `null` | ничего |
| `undefined` | ничего |
| `false` / `true` | ничего |
| `''` (пустая строка) | ничего (создаётся пустой текстовый узел) |
| `0` | **число 0** |
| `NaN` | **текст «NaN»** |
| `' '` (пробел) | пустое место |
| `[]` (пустой массив) | ничего |

Отсюда правило: условие в `&&` делаем булевым, а «пустые» значения приводим к `null` явно.

#### **3. Списки**

**`items.map(...)` — основа любого списка.**
Массивы данных React умеет рендерить напрямую: если выражение возвращает массив JSX-элементов, они выводятся друг за другом. Преобразовать массив данных в массив элементов удобнее всего методом `map`:

```tsx
const fruits = ['Яблоко', 'Груша', 'Слива'];

export function FruitList() {
  return (
    <ul>
      {fruits.map((fruit) => (
        <li key={fruit}>{fruit}</li>
      ))}
    </ul>
  );
}
```

Разберём по шагам:

*   `map` вызывается у массива и возвращает **новый** массив — исходные данные не изменяются;
*   стрелочная функция-колбэк получает один элемент массива и возвращает JSX;
*   круглые скобки после `=>` позволяют вернуть JSX без слова `return`;
*   результат `map` вставляется в разметку через `{ }`.

Обратите внимание: **если выводите список через `map`, `key` обязателен**. Без него React выведет предупреждение в консоль: `Each child in a list should have a unique "key" prop`.

Тот же приём для списка объектов:

```tsx
// src/types/product.ts
export interface Product {
  id: number;
  name: string;
  price: number;
  inStock: boolean;
}

// src/components/ProductList.tsx
import type { Product } from '../types/product';

interface ProductListProps {
  products: Product[];
}

export function ProductList({ products }: ProductListProps) {
  return (
    <ul className="product-list">
      {products.map((product) => (
        <li key={product.id} className="product-list__item">
          <h3>{product.name}</h3>
          <p>{product.price} ₽</p>
          {product.inStock ? (
            <span className="stock stock--available">В наличии</span>
          ) : (
            <span className="stock stock--unavailable">Нет в наличии</span>
          )}
        </li>
      ))}
    </ul>
  );
}
```

**Индекс и позиция элемента.**
Второй аргумент колбэка `map` — индекс элемента в массиве. Иногда он действительно нужен: для нумерации строк, для условного оформления первого и последнего элемента:

```tsx
interface User {
  id: number;
  name: string;
  email: string;
}

interface UserTableProps {
  users: User[];
}

export function UserTable({ users }: UserTableProps) {
  return (
    <table className="user-table">
      <tbody>
        {users.map((user, index) => {
          const isFirst = index === 0;
          const isLast = index === users.length - 1;
          const rowClass = [
            'user-table__row',
            isFirst ? 'user-table__row--first' : '',
            isLast ? 'user-table__row--last' : '',
          ]
            .filter(Boolean)
            .join(' ');

          return (
            <tr key={user.id} className={rowClass}>
              <td>{index + 1}</td>
              <td>{user.name}</td>
              <td>{user.email}</td>
            </tr>
          );
        })}
      </tbody>
    </table>
  );
}
```

Важно не путать: **индекс — это про позицию, а не про идентичность**. Для нумерации он подходит, для `key` — нет (об этом следующий раздел).

**Атрибут `key`: зачем он нужен.**
`key` — служебный атрибут React. Он не попадает в DOM и **не передаётся компоненту как prop**: если компоненту нужен идентификатор, его передают отдельно (`<Profile key={user.id} userId={user.id} />`).

Зачем он тогда нужен? React сравнивает предыдущее виртуальное дерево с новым и обновляет только изменившиеся узлы. В списке React должен понять, какой именно элемент:

*   остался на месте;
*   был добавлен;
*   был удалён;
*   поменялся местами с другим.

Именно `key` и есть ответ на вопрос «кто есть кто». Хороший ключ помогает React точно сопоставить элементы между рендерами и сделать точечные изменения DOM.

```tsx
// key — уникальный идентификатор из данных
{products.map((product) => (
  <ProductRow key={product.id} product={product} />
))}
```

**Что ломается без `key` и при `key={index}`.**
Если `key` не указан, React по умолчанию использует индекс. Если в качестве `key` явно передан индекс (`key={index}`) — эффект тот же: **ключ привязан к позиции, а не к элементу**. Пока список не меняется, всё работает. Как только список фильтруется, сортируется или из него удаляют элементы — начинаются трудноуловимые баги.

Наглядный пример: список карточек, внутри каждой — поле ввода и раскрытый блок. Пользователь что-то ввёл, затем список отсортировали — и данные «переехали» не в ту карточку. Причина: React считает элемент в позиции 0 тем же самым элементом, что и раньше, и сохраняет его состояние, хотя данные в позиции 0 уже другие.

```tsx
// ПЛОХО: при удалении/сортировке состояние перепутается,
// а в консоли появится предупреждение об отсутствии key
{contacts.map((contact) => (
  <ContactCard contact={contact} />
))}

// ПЛОХО: ключ по индексу — та же позиционная привязка
{contacts.map((contact, index) => (
  <ContactCard key={index} contact={contact} />
))}

// ХОРОШО: стабильный идентификатор из данных
{contacts.map((contact) => (
  <ContactCard key={contact.id} contact={contact} />
))}
```

Отдельно и категорически нельзя генерировать ключ «на лету»:

```tsx
// ОЧЕНЬ ПЛОХО: ключ меняется на каждом рендере —
// React уничтожает и создаёт элементы заново, теряя состояние и ввод пользователя
{contacts.map((contact) => (
  <ContactCard key={Math.random()} contact={contact} />
))}
```

Как выбрать `key`:

| Источник ключа | Оценка | Комментарий |
| :--- | :--- | :--- |
| `item.id` из данных | отлично | стабилен, уникален, не меняется между рендерами |
| `item.slug`, `item.email`, `item.code` | хорошо | если действительно уникальны и не меняются |
| составной ключ `\`${item.type}-${item.id}\`` | хорошо | для смешанных списков |
| индекс массива `key={index}` | плохо при изменениях | ломается при удалении, вставке, сортировке |
| `key={Math.random()}`, `key={Date.now()}` | очень плохо | список пересобирается каждый рендер |

Ещё одно правило: `key` указывается **только на самом верхнем элементе**, который возвращает колбэк `map`. Вкладывать ключ во внутренние теги не нужно.

**Фрагмент с `key` и вложенные списки.**
Если один элемент данных должен дать **несколько соседних** элементов разметки, их оборачивают во фрагмент. Короткий синтаксис `<>...</>` не принимает атрибутов, поэтому для списка нужен явный `<Fragment key={...}>`:

```tsx
// src/components/DescriptionList.tsx
import { Fragment } from 'react';

interface Term {
  id: number;
  term: string;
  definition: string;
}

interface DescriptionListProps {
  items: Term[];
}

export function DescriptionList({ items }: DescriptionListProps) {
  return (
    <dl className="terms">
      {items.map((item) => (
        <Fragment key={item.id}>
          <dt>{item.term}</dt>
          <dd>{item.definition}</dd>
        </Fragment>
      ))}
    </dl>
  );
}
```

Вложенные списки — обычные `map` внутри `map`; ключ нужен на каждом уровне:

```tsx
interface Category {
  id: number;
  title: string;
  products: Product[];
}

interface CatalogProps {
  categories: Category[];
}

export function Catalog({ categories }: CatalogProps) {
  return (
    <div className="catalog">
      {categories.map((category) => (
        <section key={category.id} className="catalog__section">
          <h2>{category.title}</h2>

          <ul>
            {category.products.map((product) => (
              <li key={product.id}>{product.name}</li>
            ))}
          </ul>
        </section>
      ))}
    </div>
  );
}
```

Ключи должны быть уникальны **внутри одного списка** — на разных уровнях они независимы.

#### **4. Фильтрация и сортировка до рендера**

Правило: готовим данные **до** `return`, а в JSX оставляем `map` по уже подготовленному массиву. Так разметка не разрастается, а логику легко прочитать и протестировать.

```tsx
interface Book {
  id: number;
  title: string;
  author: string;
  price: number;
  year: number;
}

interface BookListProps {
  books: Book[];
  query: string;
  sortBy: 'title' | 'price' | 'year';
}

export function BookList({ books, query, sortBy }: BookListProps) {
  const normalizedQuery = query.trim().toLowerCase();

  // 1. Фильтрация
  const filtered = books.filter((book) =>
    book.title.toLowerCase().includes(normalizedQuery),
  );

  // 2. Сортировка — на копии массива, без мутации props
  const sorted = [...filtered].sort((a, b) => {
    if (sortBy === 'title') {
      return a.title.localeCompare(b.title, 'ru');
    }

    return a[sortBy] - b[sortBy];
  });

  // 3. Рендер
  return (
    <ul className="book-list">
      {sorted.map((book) => (
        <li key={book.id} className="book-list__item">
          <h3>{book.title}</h3>
          <p>
            {book.author}, {book.year} — {book.price} ₽
          </p>
        </li>
      ))}
    </ul>
  );
}
```

Три важных момента:

*   **`filter` и `map` возвращают новые массивы** — исходный массив props не меняется. Это обязательное условие работы React: props доступны только для чтения.
*   **`Array.prototype.sort` мутирует массив**, поэтому сортируем копию: `[...filtered].sort(...)`. В проектах с современным `target` доступен и неизменяющий `filtered.toSorted(...)` из ES2023 — он делает то же самое, но возвращает новый массив.
*   `localeCompare` с указанием локали корректно сортирует русские строки, в отличие от простого сравнения `a.title > b.title`.

**Почему не стоит фильтровать прямо в JSX.**
Иногда пишут так:

```tsx
// Работает, но плохо читается: логика смешана с разметкой
return (
  <ul>
    {books
      .filter((book) => book.price > 1000)
      .sort((a, b) => a.title.localeCompare(b.title, 'ru'))
      .map((book) => (
        <li key={book.id}>{book.title}</li>
      ))}
  </ul>
);
```

Одна короткая цепочка допустима, но если условий несколько, лучше вынести подготовку данных в переменные с говорящими именами: `visibleBooks`, `sortedBooks`, `activeBooks`. Читающий код сразу видит три шага: фильтрация → сортировка → рендер.

**Подсчёт найденного.**
По подготовленному массиву удобно выводить статистику — и здесь снова пригодится булево условие:

```tsx
<p className="book-list__count">Найдено книг: {sorted.length}</p>

{sorted.length > 0 && (
  <p className="book-list__hint">
    Самый дорогой экземпляр: {Math.max(...sorted.map((book) => book.price))} ₽
  </p>
)}
```

#### **5. Условные `className` и `style`**

**Условный `className`.**
Классы — основной инструмент оформления состояния. В JSX `className` — это обычное строковое выражение, поэтому строку можно собрать шаблонным литералом:

```tsx
interface TodoItemProps {
  title: string;
  completed: boolean;
  isOverdue: boolean;
}

function TodoItem({ title, completed, isOverdue }: TodoItemProps) {
  return (
    <li
      className={`todo ${completed ? 'todo--completed' : ''} ${
        isOverdue ? 'todo--overdue' : ''
      }`}
    >
      {title}
    </li>
  );
}
```

Длинные шаблонные строки быстро становятся нечитаемыми, поэтому часто пишут маленькую функцию-помощник:

```tsx
// src/utils/cx.ts
// Склеивает классы, отбрасывая falsy-значения
export function cx(...classes: Array<string | false | null | undefined>): string {
  return classes.filter(Boolean).join(' ');
}
```

```tsx
import { cx } from '../utils/cx';

function TodoItem({ title, completed, isOverdue }: TodoItemProps) {
  return (
    <li className={cx('todo', completed && 'todo--completed', isOverdue && 'todo--overdue')}>
      {title}
    </li>
  );
}
```

В экосистеме есть готовые библиотеки для этой задачи (например, `clsx`), но принцип один: собираем строку классов из статической части и условных модификаторов. Классы принято именовать по схеме БЭМ (`todo`, `todo--completed`), чтобы модификатор было видно сразу.

Вариант через словарь удобен, когда состояний много:

```tsx
type OrderStatus = 'new' | 'paid' | 'shipped' | 'cancelled';

const STATUS_CLASS: Record<OrderStatus, string> = {
  new: 'order--new',
  paid: 'order--paid',
  shipped: 'order--shipped',
  cancelled: 'order--cancelled',
};

const STATUS_LABELS: Record<OrderStatus, string> = {
  new: 'Новый',
  paid: 'Оплачен',
  shipped: 'Отправлен',
  cancelled: 'Отменён',
};

export function OrderStatusLabel({ status }: { status: OrderStatus }) {
  return (
    <span className={cx('order-status', STATUS_CLASS[status])}>
      {STATUS_LABELS[status]}
    </span>
  );
}
```

**Динамический `style`.**
Инлайн-стили в JSX — объект JavaScript. В `style` передают только **действительно динамические** значения: ширину прогресса, рассчитанный цвет, координаты. Постоянное оформление живёт в CSS-классах.

```tsx
interface ProgressBarProps {
  value: number;
  max: number;
}

export function ProgressBar({ value, max }: ProgressBarProps) {
  const percent = Math.min(100, Math.round((value / max) * 100));

  return (
    <div className="progress">
      <div
        className="progress__bar"
        style={{
          width: `${percent}%`,
          backgroundColor: percent > 80 ? '#16a34a' : '#2563eb',
        }}
      />
      <span className="progress__label">{percent}%</span>
    </div>
  );
}
```

Для числовых свойств (без единиц измерения) React автоматически добавит `px`, но `width` в процентах нужно передавать строкой: `` `${percent}%` ``.

Иногда удобнее передавать значение в CSS через переменную — тогда стили остаются в CSS-файле, а из JSX приходит только число:

```tsx
import type { CSSProperties } from 'react';

interface LoaderProps {
  progress: number;
}

export function Loader({ progress }: LoaderProps) {
  const style = { '--progress': `${progress}%` } as CSSProperties;

  return <div className="loader" style={style} />;
}
```

```css
.loader::after {
  width: var(--progress, 0%);
  /* остальное оформление — в CSS */
}
```

Итог раздела:

*   состояние оформления (активный, выбранный, просроченный) — через **классы**;
*   вычисляемые геометрия и цвет — через **`style`**;
*   не дублировать в `style` то, что уже описано классом.

#### **6. Пустые состояния (empty state)**

Пустой список — нормальная ситуация, и пользователь должен понимать, что происходит. Важно различать два разных состояния:

*   **данных нет вообще** («Пока нет задач») — коллекция пустая по своей природе;
*   **ничего не найдено по условию** («По фильтру ничего не найдено») — данные есть, но не проходят фильтрацию.

Это два разных сообщения, и разные подсказки к действию: в первом случае уместно предложить создать запись, во втором — сбросить фильтр.

Универсальный компонент пустого состояния:

```tsx
// src/components/EmptyState.tsx
import type { ReactNode } from 'react';

interface EmptyStateProps {
  title: string;
  description?: string;
  action?: ReactNode;
}

export function EmptyState({ title, description, action }: EmptyStateProps) {
  return (
    <div className="empty-state" role="status">
      <h3 className="empty-state__title">{title}</h3>
      {description && <p className="empty-state__text">{description}</p>}
      {action && <div className="empty-state__action">{action}</div>}
    </div>
  );
}
```

Использование — через тернарный оператор: либо список, либо пустое состояние.

```tsx
interface TaskListProps {
  tasks: Task[];
  hasFilters: boolean;
  onResetFilters: () => void;
}

export function TaskList({ tasks, hasFilters, onResetFilters }: TaskListProps) {
  if (tasks.length === 0) {
    return hasFilters ? (
      <EmptyState
        title="По вашему запросу ничего не найдено"
        description="Попробуйте изменить условия фильтрации."
        action={
          <button type="button" onClick={onResetFilters}>
            Сбросить фильтры
          </button>
        }
      />
    ) : (
      <EmptyState
        title="Список задач пуст"
        description="Добавьте первую задачу, чтобы начать работу."
      />
    );
  }

  return (
    <ul className="task-list">
      {tasks.map((task) => (
        <TaskItem key={task.id} task={task} />
      ))}
    </ul>
  );
}
```

Ключевой приём: **проверку пустоты выполняем до `map`**, а не внутри него. Пустое состояние — это отдельная ветка рендера, а не элемент списка.

Ещё один важный случай — состояния асинхронной загрузки. Вместо двух независимых флагов (`isLoading`, `hasError`) удобнее описать одно состояние через объединение типов (discriminated union). Тогда невозможно получить «загрузка и ошибка одновременно» — компилятор не позволит:

```tsx
// src/components/DataState.tsx
import type { Item } from '../types/item';
import { EmptyState } from './EmptyState';

// Ровно одно из трёх состояний
type LoadState =
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'success'; items: Item[] };

interface DataStateProps {
  state: LoadState;
  onRetry: () => void;
}

export function DataState({ state, onRetry }: DataStateProps) {
  if (state.status === 'loading') {
    return <p className="loading" role="status">Загрузка данных...</p>;
  }

  if (state.status === 'error') {
    return (
      <div className="error" role="alert">
        <p>{state.message}</p>
        <button type="button" onClick={onRetry}>
          Повторить
        </button>
      </div>
    );
  }

  if (state.items.length === 0) {
    return <EmptyState title="Нет данных для отображения" />;
  }

  return (
    <ul className="data-list">
      {state.items.map((item) => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  );
}
```

Обратите внимание на `role="status"` и `role="alert"`: они сообщают вспомогательным технологиям (скринридерам) о смене состояния интерфейса, без них динамическое сообщение может остаться незамеченным.

#### **7. Практика: список задач с фильтром и бейджами**

Соберём небольшое приложение «Список задач»: у каждой задачи есть статус выполнения и приоритет, список можно фильтровать, а для пустого результата показывается отдельное сообщение.

**Шаг 1. Типы и данные.** Опишем модель и справочники подписей, чтобы не разбрасывать строки по компонентам:

**Шаг 3. Строка задачи.** Здесь и статус, и приоритет, и условная зачёркнутая подпись для выполненной задачи:

```tsx
// src/components/TaskItem.tsx
import type { Task } from '../types/task';
import { PriorityBadge } from './PriorityBadge';
import { cx } from '../utils/cx';

interface TaskItemProps {
  task: Task;
  onToggle: (id: number) => void;
  onDelete: (id: number) => void;
}

export function TaskItem({ task, onToggle, onDelete }: TaskItemProps) {
  const isOverdue = !task.completed && new Date(task.dueDate) < new Date();

  return (
    <li className={cx('task', task.completed && 'task--completed')}>
      <input
        type="checkbox"
        className="task__checkbox"
        checked={task.completed}
        onChange={() => onToggle(task.id)}
        aria-label={`Отметить задачу «${task.title}»`}
      />

      <div className="task__body">
        <span className="task__title">{task.title}</span>

        <div className="task__meta">
          <PriorityBadge priority={task.priority} />

          {task.completed ? (
            <span className="task__status task__status--done">Выполнено</span>
          ) : (
            <span className="task__status task__status--active">В работе</span>
          )}

          {isOverdue && <span className="badge badge--overdue">Просрочено</span>}
        </div>
      </div>

      <button
        type="button"
        className="task__delete"
        onClick={() => onDelete(task.id)}
        aria-label={`Удалить задачу «${task.title}»`}
      >
        Удалить
      </button>
    </li>
  );
}
```

Что показательно в этом компоненте:

*   `cx('task', task.completed && 'task--completed')` — условный класс через `&&`;
*   статус выводится тернарным оператором — вариантов ровно два;
*   бейдж «Просрочено» выводится через `&&` с **булевым** условием `isOverdue`;
*   `aria-label` на чекбоксе и кнопке делает управление доступным с клавиатуры и для скринридеров.

**Шаг 4. Список с фильтром.** Фильтрация и сортировка выполняются до `map`, пустое состояние — отдельная ветка:

```tsx
// src/components/TaskList.tsx
import type { Task, TaskFilter } from '../types/task';
import { FILTER_LABELS } from '../types/task';
import { TaskItem } from './TaskItem';
import { EmptyState } from './EmptyState';
import { cx } from '../utils/cx';

const FILTERS: TaskFilter[] = ['all', 'active', 'done'];

interface TaskListProps {
  tasks: Task[];
  filter: TaskFilter;
  onFilterChange: (filter: TaskFilter) => void;
  onToggle: (id: number) => void;
  onDelete: (id: number) => void;
}

export function TaskList({
  tasks,
  filter,
  onFilterChange,
  onToggle,
  onDelete,
}: TaskListProps) {
  // 1. Фильтрация до рендера
  const visibleTasks = tasks.filter((task) => {
    if (filter === 'active') {
      return !task.completed;
    }

    if (filter === 'done') {
      return task.completed;
    }

    return true;
  });

  // 2. Сортировка копии: сначала невыполненные, затем по приоритету
  const priorityRank: Record<Task['priority'], number> = { high: 0, medium: 1, low: 2 };
  const sortedTasks = [...visibleTasks].sort((a, b) => {
    if (a.completed !== b.completed) {
      return Number(a.completed) - Number(b.completed);
    }

    return priorityRank[a.priority] - priorityRank[b.priority];
  });

  const doneCount = tasks.filter((task) => task.completed).length;

  return (
    <section className="tasks">
      <header className="tasks__header">
        <h2>Список задач</h2>

        <div className="tasks__filters" role="group" aria-label="Фильтр задач">
          {FILTERS.map((value) => (
            <button
              key={value}
              type="button"
              className={cx('filter', filter === value && 'filter--active')}
              onClick={() => onFilterChange(value)}
              aria-pressed={filter === value}
            >
              {FILTER_LABELS[value]}
            </button>
          ))}
        </div>
      </header>

      {tasks.length > 0 && (
        <p className="tasks__stats">
          Всего: {tasks.length} · Выполнено: {doneCount} · Осталось: {tasks.length - doneCount}
        </p>
      )}

      {sortedTasks.length === 0 ? (
        <EmptyState
          title={filter === 'done' ? 'Выполненных задач пока нет' : 'Нет задач по выбранному фильтру'}
          description="Измените фильтр или добавьте новую задачу."
          action={
            <button type="button" onClick={() => onFilterChange('all')}>
              Показать все задачи
            </button>
          }
        />
      ) : (
        <ul className="tasks__list">
          {sortedTasks.map((task) => (
            <TaskItem key={task.id} task={task} onToggle={onToggle} onDelete={onDelete} />
          ))}
        </ul>
      )}
    </section>
  );
}
```

**Шаг 5. Сборка в `App.tsx`.** Состояние фильтра хранится в корневом компоненте и спускается вниз через props. Хуки подробно разбираются в лекции 18 — здесь достаточно увидеть, что фильтр — это обычное состояние компонента:

```tsx
// src/App.tsx
import { useState } from 'react';
import './App.css';
import type { Task, TaskFilter } from './types/task';
import { tasks as initialTasks } from './data/tasks';
import { TaskList } from './components/TaskList';

function App() {
  const [tasks, setTasks] = useState<Task[]>(initialTasks);
  const [filter, setFilter] = useState<TaskFilter>('all');

  function handleToggle(id: number) {
    setTasks((prev) =>
      prev.map((task) =>
        task.id === id ? { ...task, completed: !task.completed } : task,
      ),
    );
  }

  function handleDelete(id: number) {
    setTasks((prev) => prev.filter((task) => task.id !== id));
  }

  return (
    <main className="app">
      <h1>Мои задачи</h1>

      <TaskList
        tasks={tasks}
        filter={filter}
        onFilterChange={setFilter}
        onToggle={handleToggle}
        onDelete={handleDelete}
      />
    </main>
  );
}

export default App;
```

Обратите внимание на `handleToggle`: массив обновляется через `map`, создавая **новый** массив и новые объекты — исходные данные не мутируются. Это тот же принцип, что и с props: мы не изменяем данные, а создаём их новую версию.

### **Резюме**

*   **Условный рендеринг** в React — это обычный JavaScript: инструкция `if` до `return`, ранний выход, тернарный оператор, `&&`, `switch`.
*   Внутри `{ }` допустимо только **выражение**; инструкции `if` и `for` выносятся в тело компонента или в функцию-помощник.
*   **`null`** из компонента — нормальный способ не рендерить ничего. React не выводит `null`, `undefined`, `false` и `true`.
*   **Ловушка `&&`:** число `0` (и `NaN`) falsy, но React покажет его на экране. Слева от `&&` всегда ставим булево выражение: `items.length > 0 && ...`.
*   **Тернарный оператор** — для двух вариантов; при трёх и более используем `switch`, словарь `Record` или отдельный компонент. Вложенные тернарники — антипаттерн.
*   **Списки** строятся через `items.map(...)`; результат `map` — новый массив, исходные данные не мутируются.
*   **`key`** обязателен для каждого элемента списка и должен быть **стабильным и уникальным**: `id` из данных, а не индекс и не случайное значение. `key` не передаётся компоненту как prop.
*   **Индекс** допустим для нумерации (`index + 1`) и условного оформления первого/последнего элемента, но не как `key` в изменяемом списке.
*   **Фрагмент `<Fragment key={...}>`** нужен, когда один элемент данных порождает несколько соседних элементов разметки; короткий `<>...</>` ключ не принимает.
*   **Подготовка данных** (фильтрация, сортировка) выполняется до `return`; сортировка — на копии массива (`[...items].sort(...)`).
*   **Условное оформление:** состояние — через `className` (шаблонная строка или помощник `cx`), динамическая геометрия/цвет — через `style`; CSS-переменные позволяют держать оформление в CSS.
*   **Пустое состояние** — отдельная ветка рендера до `map`. «Данных нет» и «ничего не найдено» — разные сообщения с разными подсказками.
*   **Состояния загрузки** удобно описывать объединением типов (`loading | error | success`), а не парой независимых флагов.
*   Порядок работы с любым списком: **подготовить данные → проверить пустоту → отрендерить `map` с `key`**.

10. Почему фильтрацию и сортировку выполняют до `map`, а не внутри JSX? Почему сортировку делают на копии массива?
