### **Детальное рассмотрение каждого пункта плана:**

#### **1. Введение: Коммуникация между компонентами**

**Проблема изолированности компонентов:**
Каждый компонент в React изолирован: он управляет своим участком интерфейса и не знает о существовании соседей. Это хорошо для переиспользования, но создаёт проблему: как компоненты могут общаться друг с другом?

Ответ прост: **через данные и функции, которые передаются от родителя к детям**.

**Однонаправленный поток данных:**
В React данные текут в одном направлении:
- **Данные вниз** — от родителя к ребёнку через **props**.
- **События вверх** — от ребёнка к родителю через **колбэки** (функции, переданные как props).

Ребёнок **никогда** не изменяет props напрямую. Если что-то нужно изменить, он вызывает функцию родителя, а решение принимает родитель. Так состояние остаётся предсказуемым.

```
        ┌──────────────────────┐
        │   Родитель (state)   │
        └──────────┬───────────┘
           props ↓ │ ↑ колбэк
        ┌──────────┴───────────┐
        │       Ребёнок         │
        └──────────────────────┘
```

**Родительские и дочерние компоненты:**
```tsx
// Родитель передаёт данные вниз и получает события вверх.
function Parent() {
  const [data, setData] = useState('Значение');

  return (
    <Child
      inputData={data}
      onDataChange={setData}
    />
  );
}
```

```tsx
// Ребёнок читает props и сообщает об изменениях через вызов колбэка.
interface ChildProps {
  inputData: string;
  onDataChange: (value: string) => void;
}

function Child({ inputData, onDataChange }: ChildProps) {
  return (
    <input
      value={inputData}
      onChange={(event) => onDataChange(event.target.value)}
    />
  );
}
```

Обратите внимание: `Child` не хранит своё состояние — им управляет родитель. Это и есть однонаправленный поток данных.

#### **2. props — Передача данных «сверху вниз»**

**Синтаксис и базовое использование:**
Объявляем компонент, который принимает несколько props. Не забываем `import type` — в шаблоне Vite включён `verbatimModuleSyntax`, поэтому типы импортируются только через `import type`.

```tsx
// src/components/UserCard.tsx

// Описываем контракт props: что и в каком типе принимает компонент.
interface UserCardProps {
  userName: string;
  email: string;
  age: number;
  isActive: boolean;
}

// Компонент — обычная функция, которая принимает объект props и возвращает JSX.
export function UserCard({ userName, email, age, isActive }: UserCardProps) {
  return (
    <div className="user-card">
      <h3>{userName}</h3>
      <p>Email: {email}</p>
      <p>Возраст: {age}</p>
      <p>Статус: {isActive ? 'Активен' : 'Неактивен'}</p>
    </div>
  );
}
```

Родитель подключает компонент и передаёт значения:

```tsx
// src/App.tsx
import { UserCard } from './components/UserCard';

function App() {
  const currentUser = {
    name: 'Иван Петров',
    email: 'ivan@example.com',
    age: 30,
    isActive: true,
  };

  return (
    <UserCard
      userName={currentUser.name}
      email={currentUser.email}
      age={currentUser.age}
      isActive={currentUser.isActive}
    />
  );
}

export default App;
```

**Более удобный подход — передача объекта целиком:**
Когда свойств много, удобнее передавать один объект и описывать его отдельным интерфейсом.

```tsx
// src/types/user.ts
export interface User {
  id: number;
  name: string;
  email: string;
  age: number;
  isActive: boolean;
}
```

```tsx
// src/components/UserCard.tsx
import type { User } from '../types/user';

interface UserCardProps {
  user: User;
}

export function UserCard({ user }: UserCardProps) {
  return (
    <div className="user-card">
      <h3>{user.name}</h3>
      <p>Email: {user.email}</p>
      <p>Возраст: {user.age}</p>
      <p>Статус: {user.isActive ? 'Активен' : 'Неактивен'}</p>
    </div>
  );
}
```

```tsx
// Родитель
<UserCard user={currentUser} />
```

**Обязательные и необязательные props:**
Необязательные свойства помечаются знаком `?`, а значение по умолчанию задаётся при деструктуризации.

```tsx
interface BadgeProps {
  text: string;
  // Необязательное свойство: можно не передавать.
  variant?: 'primary' | 'success' | 'danger';
}

export function Badge({ text, variant = 'primary' }: BadgeProps) {
  return <span className={`badge badge-${variant}`}>{text}</span>;
}
```

```tsx
<Badge text="Новинка" />                       {/* variant = 'primary' */}
<Badge text="В наличии" variant="success" />   {/* variant = 'success' */}
```

Если свойство обязательное, TypeScript не даст его забыть:

```tsx
// ❌ Ошибка компиляции: отсутствует обязательное свойство text.
<Badge variant="danger" />
```

**`children` и композиция:**
React автоматически передаёт вложенную JSX-разметку в специальное свойство `children`. Это позволяет компонентам-обёрткам принимать любое содержимое.

```tsx
import type { ReactNode } from 'react';

interface CardProps {
  title: string;
  children: ReactNode;
}

export function Card({ title, children }: CardProps) {
  return (
    <section className="card">
      <h2>{title}</h2>
      <div className="card-body">{children}</div>
    </section>
  );
}
```

```tsx
<Card title="О студенте">
  <p>Иван Петров</p>
  <p>Группа ИС-21</p>
</Card>
```

Всё, что находится между открывающим и закрывающим тегом `<Card>`, попадает в `children`. Это основной механизм **композиции** в React.

#### **3. События — Отправка событий «снизу вверх» через колбэки**

**Передача функций как props:**
Ребёнок не может изменить состояние родителя. Вместо этого родитель передаёт ребёнку функцию-обработчик, а ребёнок вызывает её в нужный момент.

```tsx
// src/components/Button.tsx
interface ButtonProps {
  label: string;
  disabled?: boolean;
  // Колбэк без аргументов и без возвращаемого значения.
  onClick: () => void;
}

export function Button({ label, disabled = false, onClick }: ButtonProps) {
  return (
    <button type="button" disabled={disabled} onClick={onClick}>
      {label}
    </button>
  );
}
```

```tsx
// Родитель решает, что произойдёт при нажатии.
function SavePanel() {
  const [isSaving, setIsSaving] = useState(false);

  const handleSave = () => {
    setIsSaving(true);
    // ...отправка данных на сервер
  };

  return (
    <Button label="Сохранить" disabled={isSaving} onClick={handleSave} />
  );
}
```

**Соглашение об именовании:** prop-колбэк обычно называют `on<Событие>` (`onDelete`, `onChange`, `onSearch`), а функцию-обработчик в родителе — `handle<Событие>` (`handleDelete`, `handleChange`). Это не требование React, но так код читается однозначно.

**Типизация callback-пропсов:**
Функция передаётся как обычное значение, поэтому её тип описывается в интерфейсе props.

```tsx
interface SearchBoxProps {
  placeholder?: string;
  // Принимает строку и ничего не возвращает.
  onSearchChange: (query: string) => void;
}

export function SearchBox({
  placeholder = 'Поиск...',
  onSearchChange,
}: SearchBoxProps) {
  return (
    <input
      type="search"
      placeholder={placeholder}
      onChange={(event) => onSearchChange(event.target.value)}
    />
  );
}
```

```tsx
// Родитель
function UsersPage() {
  const [query, setQuery] = useState('');

  return (
    <SearchBox
      placeholder="Поиск пользователей..."
      onSearchChange={setQuery}   // setQuery имеет тип (value: string) => void
    />
  );
}
```

Обратите внимание: `setQuery` из `useState` уже имеет нужную сигнатуру, поэтому его можно передать напрямую. Но если логика сложнее, пишут отдельный обработчик:

```tsx
const handleSearchChange = (value: string) => {
  setQuery(value);
  // Здесь можно добавить, например, сброс страницы пагинации.
};
```

**Типы событий DOM:**
Если колбэк принимает не значение, а само событие, используется тип из React:

```tsx
import type { ChangeEvent } from 'react';

interface PhoneInputProps {
  value: string;
  onChange: (event: ChangeEvent<HTMLInputElement>) => void;
}

export function PhoneInput({ value, onChange }: PhoneInputProps) {
  return <input type="tel" value={value} onChange={onChange} />;
}
```

**Передача данных вместе с событием:**
Часто ребёнку нужно сообщить не просто «нажали», а «нажали вот на эту строку».

```tsx
// Компонент рейтинга: сообщает родителю выбранное число звёзд.
interface RatingProps {
  value: number;
  onChange: (value: number) => void;
}

export function Rating({ value, onChange }: RatingProps) {
  return (
    <div className="rating">
      {[1, 2, 3, 4, 5].map((star) => (
        <button
          key={star}
          type="button"
          className={star <= value ? 'star active' : 'star'}
          aria-label={`Оценка ${star}`}
          onClick={() => onChange(star)}
        >
          ★
        </button>
      ))}
    </div>
  );
}
```

```tsx
// Родитель хранит оценку и реагирует на выбор.
function UserRating() {
  const [userRating, setUserRating] = useState(0);

  return (
    <>
      <Rating value={userRating} onChange={setUserRating} />
      <p>Пользователь оценил на: {userRating} из 5</p>
    </>
  );
}
```

Дочерний компонент ничего не знает о том, как родитель использует оценку. Он лишь сообщает: «выбрали значение `star`».

#### **4. Подъём состояния (lifting state up)**

**Единственный источник истины:**
Если два компонента должны видеть одни и те же данные и синхронно на них реагировать, состояние поднимают к их ближайшему общему родителю. Это называется **подъёмом состояния** (lifting state up).

Частая ошибка новичка — хранить производные данные в отдельном `useState`:

```tsx
// ❌ Плохо: два источника истины, которые нужно синхронизировать вручную.
const [users, setUsers] = useState<User[]>(initialUsers);
const [filteredUsers, setFilteredUsers] = useState<User[]>(initialUsers);

const handleSearch = (query: string) => {
  setFilteredUsers(users.filter((u) => u.name.includes(query)));
};
```

Правильно — хранить исходные данные и **вычислять** производные во время рендера:

```tsx
// ✅ Хорошо: filteredUsers — вычисляемое значение, а не отдельное состояние.
const [users, setUsers] = useState<User[]>(initialUsers);
const [query, setQuery] = useState('');

const filteredUsers = users.filter((user) =>
  user.name.toLowerCase().includes(query.toLowerCase()),
);
```

**Пример: поиск и фильтрация списка:**
Родитель владеет и списком, и строкой поиска, а презентационный компонент `SearchBox` только сообщает о вводе.

```tsx
// src/pages/UsersPage.tsx
import { useState } from 'react';
import type { User } from '../types/user';
import { SearchBox } from '../components/SearchBox';
import { UserList } from '../components/UserList';

const initialUsers: User[] = [
  { id: 1, name: 'Анна Иванова', email: 'anna@company.com', age: 25, isActive: true },
  { id: 2, name: 'Пётр Сидоров', email: 'petr@company.com', age: 34, isActive: false },
  { id: 3, name: 'Мария Козлова', email: 'maria@company.com', age: 29, isActive: true },
];

export function UsersPage() {
  // Источник истины — родитель.
  const [users] = useState<User[]>(initialUsers);
  const [query, setQuery] = useState('');

  // Производное значение пересчитывается при каждом рендере.
  const filteredUsers = users.filter(
    (user) =>
      user.name.toLowerCase().includes(query.toLowerCase()) ||
      user.email.toLowerCase().includes(query.toLowerCase()),
  );

  return (
    <div className="users-page">
      <h1>Список пользователей</h1>
      <SearchBox placeholder="Поиск по имени или email..." onSearchChange={setQuery} />
      <UserList users={filteredUsers} />
    </div>
  );
}
```

Такой код проще тестировать и сопровождать: состояние живёт в одном месте, а компоненты ниже остаются «глупыми» и переиспользуемыми.

#### **5. Context — Общее состояние без «пробрасывания» props**

**Проблема prop drilling:**
Если данные нужны глубоко в дереве, их приходится передавать через все промежуточные компоненты, даже если они сами эти данные не используют. Это называют **prop drilling** («пробрасывание props»).

```tsx
function App() {
  const [theme, setTheme] = useState('light');
  return <Layout theme={theme} setTheme={setTheme} />;
}

function Layout({ theme, setTheme }: LayoutProps) {
  // Layout сам тему не использует, но обязан передать дальше.
  return <Sidebar theme={theme} setTheme={setTheme} />;
}

function Sidebar({ theme, setTheme }: SidebarProps) {
  return <ThemeToggle theme={theme} setTheme={setTheme} />;
}
```

Context решает эту проблему: значение становится доступно любому потомку провайдера напрямую, без промежуточных props.

**`createContext`, `Provider`, `useContext`:**
Создаём контекст, компонент-провайдер и собственный хук доступа.

```tsx
// src/context/ThemeContext.tsx
import { createContext, useContext, useMemo, useState } from 'react';
import type { ReactNode } from 'react';

type Theme = 'light' | 'dark';

// Описываем всё, что будет доступно потребителям контекста.
interface ThemeContextValue {
  theme: Theme;
  toggleTheme: () => void;
  setTheme: (theme: Theme) => void;
}

// Начальное значение null — это признак «контекст ещё не предоставлен».
const ThemeContext = createContext<ThemeContextValue | null>(null);

interface ThemeProviderProps {
  children: ReactNode;
}

export function ThemeProvider({ children }: ThemeProviderProps) {
  const [theme, setTheme] = useState<Theme>('light');

  const toggleTheme = () => {
    setTheme((prev) => (prev === 'light' ? 'dark' : 'light'));
  };

  // useMemo не даёт создавать новый объект значения на каждом рендере.
  const value = useMemo<ThemeContextValue>(
    () => ({ theme, toggleTheme, setTheme }),
    [theme],
  );

  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}

// Собственный хук: единая точка доступа к контексту.
export function useTheme(): ThemeContextValue {
  const context = useContext(ThemeContext);

  // Понятная ошибка вместо загадочного «cannot read property theme of null».
  if (context === null) {
    throw new Error('useTheme должен вызываться внутри ThemeProvider');
  }

  return context;
}
```

Разберём ключевые моменты:
- `createContext<ThemeContextValue | null>(null)` — типизируем контекст и разрешаем значение `null` по умолчанию.
- `ThemeContext.Provider` — компонент, который «предоставляет» значение всем потомкам.
- `useContext(ThemeContext)` — читает ближайшее значение провайдера.
- Собственный хук `useTheme` **инкапсулирует проверку** и делает код потребителей чище.

**Потребитель контекста:**
```tsx
// src/components/ThemeToggle.tsx
import { useTheme } from '../context/ThemeContext';

export function ThemeToggle() {
  const { theme, toggleTheme } = useTheme();

  return (
    <button type="button" onClick={toggleTheme}>
      {theme === 'light' ? '🌙 Тёмная тема' : '☀️ Светлая тема'}
    </button>
  );
}
```

Компонент `ThemeToggle` можно разместить на любой глубине дерева внутри `ThemeProvider` — props через промежуточные компоненты передавать не нужно.

**Композиция нескольких провайдеров:**
В реальном приложении контекстов несколько. Их удобно собрать в один компонент `AppProviders`.

```tsx
// src/app/AppProviders.tsx
import type { ReactNode } from 'react';
import { ThemeProvider } from '../context/ThemeContext';
import { AuthProvider } from '../context/AuthContext';
import { ToastProvider } from '../context/ToastContext';

interface AppProvidersProps {
  children: ReactNode;
}

export function AppProviders({ children }: AppProvidersProps) {
  return (
    <ThemeProvider>
      <AuthProvider>
        <ToastProvider>{children}</ToastProvider>
      </AuthProvider>
    </ThemeProvider>
  );
}
```

```tsx
// src/main.tsx
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import './index.css';
import App from './App';
import { AppProviders } from './app/AppProviders';

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <AppProviders>
      <App />
    </AppProviders>
  </StrictMode>,
);
```

**Важно помнить:** при изменении значения контекста перерисовываются **все** его потребители. Поэтому:
- храните в одном контексте логически связанные данные (тема — отдельно, авторизация — отдельно);
- не кладите в контекст то, что можно передать обычными props.

**Когда контекст уместен, а когда достаточно props:**

| Ситуация | Решение |
|----------|---------|
| Данные нужны одному-двум прямым детям | Обычные **props** |
| Значение нужно многим компонентам на разной глубине | **Context** |
| Редко меняющиеся глобальные данные (тема, язык, текущий пользователь) | **Context** |
| Часто меняющиеся данные, сложная логика, кэш сервера | Специализированные библиотеки (в лекции 23 — Zustand) |

Правило простое: **начинайте с props**. Context подключайте, когда появляется реальное «пробрасывание» через несколько уровней.

#### **6. Практические паттерны**

**Компонент-контейнер и презентационные компоненты:**
Разделим ответственность:
- **Контейнер** («умный» компонент) владеет состоянием и логикой, обрабатывает события.
- **Презентационные** компоненты только отображают данные и вызывают переданные колбэки.

```tsx
// Контейнер владеет состоянием и логикой.
function UserListContainer() {
  const [users, setUsers] = useState<User[]>(initialUsers);

  const handleDelete = (userId: number) => {
    setUsers((prev) => prev.filter((user) => user.id !== userId));
  };

  const handleSelect = (user: User) => {
    console.log('Выбран пользователь:', user);
  };

  return (
    <UserList
      users={users}
      onDelete={handleDelete}
      onSelect={handleSelect}
    />
  );
}
```

**Компонент списка с действиями:**
Презентационный компонент ничего не удаляет сам — он сообщает о намерении.

```tsx
// src/components/UserList.tsx
import type { User } from '../types/user';

interface UserListProps {
  users: User[];
  isLoading?: boolean;
  // Колбэки: ребёнок сообщает о действии, решение принимает родитель.
  onDelete: (userId: number) => void;
  onSelect: (user: User) => void;
}

export function UserList({ users, isLoading = false, onDelete, onSelect }: UserListProps) {
  if (isLoading) {
    return <p>Загрузка...</p>;
  }

  if (users.length === 0) {
    return <p>Пользователи не найдены</p>;
  }

  return (
    <div className="user-list">
      {users.map((user) => (
        <div key={user.id} className="user-item">
          <span>{user.name}</span>
          <span>{user.email}</span>
          <div className="actions">
            <button type="button" aria-label={`Профиль ${user.name}`} onClick={() => onSelect(user)}>
              👁️
            </button>
            <button type="button" aria-label={`Удалить ${user.name}`} onClick={() => onDelete(user.id)}>
              🗑️
            </button>
          </div>
        </div>
      ))}
    </div>
  );
}
```

Обратите внимание на `key={user.id}` — React использует ключ, чтобы правильно сопоставлять элементы списка при обновлении.

**Шаг 3. Страница списка** — владеет данными и фильтрацией, использует тему из контекста.

```tsx
// src/pages/UserListPage.tsx
import { useState } from 'react';
import type { User } from '../types/user';
import { useTheme } from '../context/ThemeContext';
import { ThemeToggle } from '../components/ThemeToggle';
import { SearchBox } from '../components/SearchBox';
import { UserCard } from '../components/UserCard';

const mockUsers: User[] = [
  { id: 1, name: 'Анна Иванова', email: 'anna@company.com', age: 25, isActive: true },
  { id: 2, name: 'Пётр Сидоров', email: 'petr@company.com', age: 34, isActive: false },
  { id: 3, name: 'Мария Козлова', email: 'maria@company.com', age: 29, isActive: true },
];

export function UserListPage() {
  // Тема приходит из контекста — props через посредников не нужны.
  const { theme } = useTheme();

  // Список и строка поиска — состояние родителя (единственный источник истины).
  const [users, setUsers] = useState<User[]>(mockUsers);
  const [query, setQuery] = useState('');

  // Производное значение: фильтруем список при рендере.
  const filteredUsers = users.filter(
    (user) =>
      user.name.toLowerCase().includes(query.toLowerCase()) ||
      user.email.toLowerCase().includes(query.toLowerCase()),
  );

  // Событие «снизу вверх»: удаляем пользователя по id.
  const handleDeleteUser = (userId: number) => {
    setUsers((prev) => prev.filter((user) => user.id !== userId));
  };

  const handleResetFilters = () => {
    setQuery('');
  };

  return (
    <div className={`user-list-page theme-${theme}`}>
      <header className="page-header">
        <h1>Список пользователей</h1>
        <p>Всего пользователей: {users.length}</p>
        <ThemeToggle />
      </header>

      <div className="filters">
        <SearchBox
          placeholder="Поиск по имени или email..."
          onSearchChange={setQuery}
        />
      </div>

      <div className="user-grid">
        {filteredUsers.map((user) => (
          <UserCard key={user.id} user={user} onDelete={handleDeleteUser} />
        ))}

        {filteredUsers.length === 0 && (
          <div className="empty-state">
            <p>😔 Пользователи не найдены</p>
            <button type="button" onClick={handleResetFilters}>
              Сбросить фильтры
            </button>
          </div>
        )}
      </div>
    </div>
  );
}
```

Обратите внимание на разделение ролей:
- **`UserListPage`** владеет состоянием `users` и `query`, принимает решения об удалении.
- **`UserCard`** только отображает данные и вызывает `onDelete(user.id)`.
- **`ThemeContext`** избавляет от передачи темы через промежуточные компоненты.
- **`SearchBox`** не хранит строку поиска — она живёт у родителя (подъём состояния).

**Шаг 4. Точка входа** — оборачиваем приложение в `ThemeProvider`.

```tsx
// src/App.tsx
import { ThemeProvider } from './context/ThemeContext';
import { UserListPage } from './pages/UserListPage';

function App() {
  return (
    <ThemeProvider>
      <UserListPage />
    </ThemeProvider>
  );
}

export default App;
```

**Анонс: глобальное состояние и Zustand.**
Context отлично подходит для редко меняющихся данных: тема, язык, текущий пользователь. Но если в контексте хранить часто обновляемое состояние (например, большой список с фильтрами и серверной синхронизацией), перерисовка всех потребителей может стать узким местом. В лекции 23 мы познакомимся с библиотекой **Zustand** — лёгким менеджером глобального состояния, который решает эту задачу аккуратнее и не требует оборачивать дерево в провайдеры.

### **Резюме**

*   **props** — данные «сверху вниз»: родитель передаёт их как атрибуты JSX.
*   **Колбэки** — события «снизу вверх»: ребёнок вызывает функцию, переданную родителем.
*   **Однонаправленный поток данных** — основа предсказуемости приложения.
*   **`children`** — механизм композиции: любая JSX-разметка между тегами компонента.
*   **Подъём состояния** — общее состояние живёт у ближайшего общего родителя, производные значения вычисляются, а не дублируются в `useState`.
*   **Context** (`createContext` → `Provider` → `useContext`) убирает «пробрасывание» props через промежуточные компоненты.
*   Собственный хук `useTheme` с проверкой на `null` даёт понятную ошибку и чистый API.
*   **Когда Context:** много потребителей, разная глубина, редко меняющиеся данные.
*   **Когда props:** один-два получателя, локальные данные — props проще и прозрачнее.

**Ключевые принципы:**
- Родительский компонент управляет состоянием.
- Дочерние компоненты получают данные через props.
- Дочерние компоненты сообщают о действиях через колбэки.
- Не изменяйте props и не дублируйте производные данные в состоянии.
- Для глобального состояния используйте Context (позже — Zustand).
