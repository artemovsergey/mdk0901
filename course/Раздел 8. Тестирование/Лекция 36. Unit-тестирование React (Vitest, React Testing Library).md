### **Детальное рассмотрение каждого пункта плана:**

#### **1. Зачем нужны тесты**

**Что даёт автоматическое тестирование?**

Тест — это код, который проверяет другой код. Вместо того чтобы после каждой правки вручную открывать браузер и кликать по кнопкам, мы один раз описываем ожидаемое поведение, а затем специальная программа (тест-раннер) проверяет его за секунды.

Автоматические тесты дают:

*   **Раннее обнаружение ошибок.** Ошибку видно сразу после запуска тестов, а не через неделю в production.
*   **Уверенность при рефакторинге.** Если тесты зелёные, изменение внутренней структуры не сломало поведение.
*   **Живую документацию.** Тест показывает, как компонент предполагается использовать и что он должен делать.
*   **Более качественный дизайн.** Код, который легко тестировать, обычно слабее связан и чище разделён по ответственностям.

**Пирамида тестирования:**

```
        /\
       /  \     E2E-тесты          (мало, медленные, дорогие)
      /____\
     /      \   Интеграционные     (средне)
    /________\  Unit-тесты         (много, быстрые, дешёвые)
```

Чем ниже уровень, тем больше тестов и тем они быстрее. Основание пирамиды — unit-тесты.

**Уровни тестирования:**

| Уровень | Что проверяет | Скорость | Инструменты в курсе |
|---------|---------------|----------|---------------------|
| **Unit** | Отдельный компонент, функция или хук в изоляции | Очень высокая | Vitest + React Testing Library |
| **Интеграционные** | Совместную работу нескольких компонентов и модулей | Средняя | Vitest + RTL (несколько компонентов), Playwright-компоненты |
| **E2E (end-to-end)** | Всё приложение целиком в реальном браузере через реальный API | Низкая | Playwright |

**Место unit-тестов:**

Unit-тест проверяет **одну единицу поведения** и не должен зависеть от базы данных, сети, других компонентов или случайного порядка запуска. В React единицей чаще всего выступает:

*   компонент (как ведёт себя интерфейс при действиях пользователя);
*   кастомный хук (как меняется его состояние);
*   чистая функция-утилита (форматирование, вычисления).

> **Важно:** unit-тесты не заменяют ручную проверку и E2E, а дополняют их. Дешёвые и быстрые тесты берут на себя основную массу проверок, оставляя E2E самое главное — сквозные сценарии.

#### **2. Vitest — тест-раннер для Vite-проектов**

**Почему Vitest?**

Vitest — современный тест-раннер, созданный той же командой, что и Vite. Его ключевые преимущества:

| Возможность | Что это значит на практике |
|-------------|----------------------------|
| **Нативность для Vite** | Использует ту же конфигурацию и тот же конвейер трансформации, что и сборка. Отдельный сборщик для тестов не нужен. |
| **Совместимый API** | `describe`, `it`, `expect`, `beforeEach` — синтаксис, знакомый по Jest. Переход почти без переучивания. |
| **Скорость и watch** | Быстрый запуск, умный watch-режим: перезапускаются только затронутые тесты. |
| **ESM и TypeScript «из коробки»** | Не нужны дополнительные транспиляторы и настройки. |
| **Покрытие кода** | Встроенная поддержка coverage через провайдер V8. |
| **Моки** | Мощный API: `vi.fn`, `vi.mock`, `vi.spyOn`, fake timers. |

**Установка:**

```bash
# Основные пакеты для тестирования React-компонентов
npm i -D vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event

# Провайдер покрытия (нужен для команды --coverage)
npm i -D @vitest/coverage-v8
```

Разберём назначение пакетов:

| Пакет | Зачем нужен |
|-------|-------------|
| `vitest` | Сам тест-раннер: `describe`, `it`, `expect`, `vi`. |
| `jsdom` | Эмуляция DOM в Node.js — тесты идут без реального браузера. |
| `@testing-library/react` | `render`, `screen`, `renderHook`, `waitFor` для React. |
| `@testing-library/jest-dom` | Дополнительные матчеры DOM (`toBeInTheDocument`, `toBeDisabled` и др.). |
| `@testing-library/user-event` | Реалистичная имитация действий пользователя. |
| `@vitest/coverage-v8` | Подсчёт покрытия кода тестами. |

**npm-скрипты (`package.json`):**

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview",
    "test": "vitest",
    "test:run": "vitest run",
    "coverage": "vitest run --coverage"
  }
}
```

*   `npm test` — запускает Vitest в **watch-режиме**: тесты перезапускаются при изменении файлов (удобно во время разработки).
*   `npm run test:run` — **однократный** прогон всех тестов (используется в CI и при сдаче работы).
*   `npm run coverage` — однократный прогон с отчётом о покрытии.

> Команда `vitest` без аргументов по умолчанию работает в watch-режиме, поэтому в CI и на «холодном» запуске всегда используйте `vitest run`.

**Конфигурация `vite.config.ts`:**

Настройки тестов добавляются прямо в конфиг Vite. Импортируем `defineConfig` из `vitest/config` — он расширяет обычный конфиг Vite секцией `test`:

```ts
/// <reference types="vitest/config" />
import { defineConfig } from 'vitest/config';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: {
    // Среда с DOM — эмулирует браузер для тестов компонентов
    environment: 'jsdom',
    // Глобальные describe/it/expect/vi — их не нужно импортировать в каждом файле
    globals: true,
    // Файл, который выполняется перед каждым тестовым файлом
    setupFiles: './src/test/setup.ts',
    // Подключать CSS-файлы в тестах (по умолчанию они игнорируются)
    css: true,
    // Настройки отчёта о покрытии
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html'],
    },
  },
});
```

**Файл `src/test/setup.ts`:**

Это общая инициализация тестового окружения. Здесь подключаются матчеры jest-dom:

```ts
// src/test/setup.ts
import '@testing-library/jest-dom/vitest';
```

> Путь именно `@testing-library/jest-dom/vitest` — он регистрирует матчеры так, чтобы их «увидел» `expect` из Vitest. Импорт без `/vitest` рассчитан на Jest и в Vitest не подойдёт.

**Типы для глобальных функций (`tsconfig.app.json`):**

Чтобы TypeScript знал про глобальные `describe`, `it`, `expect` и `vi`, добавьте типы Vitest:

```json
{
  "compilerOptions": {
    "types": ["vitest/globals"]
  }
}
```

Если вы не хотите включать `globals`, импортируйте функции явно в каждом тестовом файле:

```ts
import { describe, it, expect, vi, beforeEach } from 'vitest';
```

> В проектах курса с включённым `verbatimModuleSyntax` типы импортируются отдельно: `import type { User } from './types'`. Это правило действует и в тестах.

#### **3. React Testing Library: философия и запросы**

**Философия: тестируем поведение, а не реализацию**

React Testing Library (RTL) — библиотека для проверки компонентов так, как их видит **пользователь**. Основной принцип сформулирован её авторами:

> Чем больше тесты похожи на то, как приложение используют люди, тем больше уверенности они дают.

Это значит:

*   мы ищем элементы **по доступным признакам** (роль, подпись, текст), а не по CSS-классам и внутренним переменным;
*   мы **взаимодействуем** с интерфейсом (кликаем, вводим текст), а не вызываем внутренние методы компонента;
*   мы проверяем **видимый результат**, а не внутреннее состояние.

Если тест приходится переписывать после безопасного рефакторинга (например, после переименования CSS-класса), скорее всего, он тестировал детали реализации — а не поведение.

**`render` и `screen`:**

`render` монтирует компонент в виртуальный DOM, а `screen` даёт доступ к этому DOM:

```tsx
import { render, screen } from '@testing-library/react';
import { Counter } from './Counter';

render(<Counter />);

// screen.getByText ищет элемент во всём отрендеренном дереве
const heading = screen.getByText('Счётчик: 0');
```

**Приоритет запросов:**

Не все способы поиска одинаково хороши. Правило: **чем ближе запрос к тому, как элемент воспринимает пользователь и вспомогательные технологии, тем он лучше**.

| Приоритет | Запрос | Когда использовать |
|-----------|--------|--------------------|
| 1 (лучший) | `getByRole` | Кнопки, поля, заголовки, чекбоксы — ищите по роли и доступному имени: `getByRole('button', { name: 'Сохранить' })` |
| 2 | `getByLabelText` | Поля форм, связанные с `<label>` |
| 3 | `getByPlaceholderText` | Когда нет подписи (крайний случай) |
| 4 | `getByText` | Обычный текст: абзацы, заголовки, подписи |
| 5 | `getByDisplayValue` | Значение, введённое в поле |
| 6 (худший) | `getByTestId` | Когда надёжнее ничего нет; требует `data-testid` в разметке |

> Запросы по роли и подписи заодно проверяют **доступность**: если элемент не находится по роли, возможно, у него проблемы для пользователей скринридеров.

**Три варианта каждого запроса:**

| Вариант | Возвращает | Когда использовать |
|---------|-----------|--------------------|
| `getBy*` | Элемент или **бросает ошибку**, если не найдено | Элемент должен присутствовать прямо сейчас |
| `queryBy*` | Элемент или `null` | Проверка **отсутствия**: `expect(screen.queryByText('Ошибка')).not.toBeInTheDocument()` |
| `findBy*` | **Promise**, ждёт появления элемента | После асинхронных операций |

Пример на все три варианта:

```tsx
// Присутствует сейчас — getBy
expect(screen.getByRole('heading')).toHaveTextContent('Список задач');

// Отсутствует — только queryBy (getBy здесь бы бросил ошибку)
expect(screen.queryByText('Задач нет')).not.toBeInTheDocument();

// Появится после загрузки — findBy (асинхронно)
expect(await screen.findByText('Анна')).toBeInTheDocument();
```

#### **4. События пользователя и асинхронность**

**`user-event` вместо `fireEvent`**

`fireEvent` — низкоуровневая утилита: она просто диспатчит одно событие. `user-event` моделирует **реальный поток событий**, который браузер генерирует при действии человека. Например, `user.type` эмитит последовательность `keydown`/`keypress`/`input`/`keyup` для каждого символа, а `user.click` — события фокуса, мыши и наведения.

**Предпочитайте `@testing-library/user-event`** — тесты получаются ближе к реальному поведению.

```tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { LoginForm } from './LoginForm';

it('передаёт введённый email при отправке формы', async () => {
  // Arrange: создаём «пользователя» и обработчик-шпион
  const user = userEvent.setup();
  const handleSubmit = vi.fn();
  render(<LoginForm onSubmit={handleSubmit} />);

  // Act: вводим текст и кликаем
  const input = screen.getByLabelText('Email');
  await user.type(input, 'student@example.com');
  await user.click(screen.getByRole('button', { name: 'Войти' }));

  // Assert
  expect(input).toHaveValue('student@example.com');
  expect(handleSubmit).toHaveBeenCalledWith('student@example.com');
});
```

Основные методы `user-event`:

| Метод | Что делает |
|-------|-----------|
| `user.click(element)` | Клик мышью |
| `user.type(element, 'текст')` | Посимвольный ввод текста |
| `user.clear(element)` | Очистка поля |
| `user.selectOptions(select, 'value')` | Выбор опции в `<select>` |
| `user.hover(element)` | Наведение курсора |
| `user.tab()` | Нажатие Tab (проверка порядка фокуса) |
| `user.keyboard('{Enter}')` | Нажатие клавиш, включая спецпоследовательности |

> Почти все методы `user-event` асинхронные — их нужно вызывать с `await`. Обязательно вызывайте `userEvent.setup()` **перед** `render`, чтобы настройки применились к DOM.

**Асинхронность: `findBy*` и `waitFor`**

Компонент может загружать данные из API. В момент рендера списка ещё нет — он появится позже. `findBy*` ждёт появления элемента (по умолчанию до 1000 мс, с повторными проверками):

```tsx
// find* — удобный «ожидающий» запрос
const item = await screen.findByText('Анна');
expect(item).toBeInTheDocument();
```

`waitFor` нужен, когда мы ждём **не появления элемента**, а наступления другого условия — например, вызова функции:

```tsx
import { render, screen, waitFor } from '@testing-library/react';

render(<UserList />);

await waitFor(() => {
  expect(screen.getByText('Анна')).toBeInTheDocument();
});
```

> `findBy*` — это, по сути, обёртка над `waitFor` + `getBy*`. Если вам нужен конкретный элемент — берите `findBy*`, он короче и читаемее.

#### **5. Моки и тестирование хуков**

**Три инструмента мокирования в Vitest:**

| Инструмент | Назначение | Пример |
|------------|-----------|--------|
| `vi.fn()` | Создать функцию-заглушку (шпион), которая запоминает вызовы | `const onSubmit = vi.fn();` |
| `vi.mock(path)` | Заменить **весь модуль** на автоматические заглушки | `vi.mock('./api/users');` |
| `vi.spyOn(obj, 'method')` | «Проследить» за методом существующего объекта, при необходимости подменить реализацию | `vi.spyOn(console, 'error').mockImplementation(() => {});` |

**Мок API-модуля и асинхронный компонент**

Пусть есть модуль, который ходит на сервер:

```ts
// src/api/users.ts
export interface User {
  id: number;
  name: string;
}

export async function fetchUsers(): Promise<User[]> {
  const response = await fetch('/api/users');
  if (!response.ok) {
    throw new Error('Не удалось загрузить пользователей');
  }
  return (await response.json()) as User[];
}
```

Компонент загружает список через `useEffect`:

```tsx
// src/components/UserList.tsx
import { useEffect, useState } from 'react';
import { fetchUsers } from '../api/users';
import type { User } from '../api/users';

export function UserList() {
  const [users, setUsers] = useState<User[]>([]);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    fetchUsers()
      .then(setUsers)
      .catch((reason: unknown) => {
        setError(reason instanceof Error ? reason.message : 'Неизвестная ошибка');
      })
      .finally(() => setIsLoading(false));
  }, []);

  if (isLoading) {
    return <p>Загрузка…</p>;
  }

  if (error) {
    return <p role="alert">{error}</p>;
  }

  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

Теперь тест: подменяем модуль API и управляем ответом через `vi.mocked`:

```tsx
// src/components/UserList.test.tsx
import { render, screen } from '@testing-library/react';
import { UserList } from './UserList';
import { fetchUsers } from '../api/users';

// vi.mock обязан находиться на верхнем уровне файла (поднимается в начало)
vi.mock('../api/users');

const mockedFetchUsers = vi.mocked(fetchUsers);

describe('UserList', () => {
  it('сначала показывает загрузку, затем список пользователей', async () => {
    // Arrange: задаём, что вернёт «сервер»
    mockedFetchUsers.mockResolvedValue([
      { id: 1, name: 'Анна' },
      { id: 2, name: 'Иван' },
    ]);

    // Act
    render(<UserList />);

    // Assert: сначала индикатор, затем данные
    expect(screen.getByText('Загрузка…')).toBeInTheDocument();
    expect(await screen.findByText('Анна')).toBeInTheDocument();
    expect(screen.getByText('Иван')).toBeInTheDocument();
    expect(screen.queryByText('Загрузка…')).not.toBeInTheDocument();
  });

  it('показывает сообщение об ошибке, если запрос упал', async () => {
    mockedFetchUsers.mockRejectedValue(new Error('Сервер недоступен'));

    render(<UserList />);

    expect(await screen.findByRole('alert')).toHaveTextContent('Сервер недоступен');
  });
});
```

> `vi.mock('../api/users')` без фабрики заменяет все экспорты модуля на заглушки. `vi.mocked(fetchUsers)` — это типизированный доступ к заглушке, чтобы TypeScript знал про `mockResolvedValue` и `mockRejectedValue`.

**Тестирование кастомных хуков через `renderHook`**

Хук нельзя отрендерить как обычный компонент, поэтому RTL предоставляет `renderHook`. Результат вызова доступен в `result.current`, а изменения состояния нужно оборачивать в `act`:

```tsx
// src/hooks/useToggle.ts
import { useCallback, useState } from 'react';

export function useToggle(initial = false) {
  const [value, setValue] = useState(initial);
  const toggle = useCallback(() => setValue((current) => !current), []);
  return { value, toggle };
}
```

```tsx
// src/hooks/useToggle.test.ts
import { act, renderHook } from '@testing-library/react';
import { useToggle } from './useToggle';

describe('useToggle', () => {
  it('переключает значение при вызове toggle', () => {
    const { result } = renderHook(() => useToggle());

    expect(result.current.value).toBe(false);

    // Изменение состояния оборачиваем в act
    act(() => {
      result.current.toggle();
    });

    expect(result.current.value).toBe(true);
  });
});
```

**Fake timers**

Если компонент использует `setTimeout`/`setInterval` (таймеры, debounce), реальное ожидание сделает тесты медленными. Vitest позволяет подменить таймеры:

```ts
import { beforeEach, afterEach } from 'vitest';

beforeEach(() => {
  vi.useFakeTimers();
});

afterEach(() => {
  vi.useRealTimers();
});

it('скрывает уведомление через 3 секунды', () => {
  // ... render ...
  vi.advanceTimersByTime(3000);
  // ... проверка ...
});
```

> С fake timers будьте осторожны: `waitFor` и `findBy*` тоже полагаются на таймеры. Если они «зависают», настройте `vi.useFakeTimers()` так, чтобы не подменять очередь микрозадач, либо верните реальные таймеры перед асинхронными проверками.

#### **6. Паттерн AAA, изоляция и что не нужно тестировать**

**Паттерн Arrange — Act — Assert (AAA)**

Хороший тест читается как короткая история из трёх частей:

1.  **Arrange (подготовка)** — создаём данные, моки, рендерим компонент.
2.  **Act (действие)** — выполняем то, что тестируем: клик, ввод, вызов.
3.  **Assert (проверка)** — проверяем результат.

```tsx
it('не добавляет пустую задачу', async () => {
  // Arrange
  const user = userEvent.setup();
  render(<TodoList />);

  // Act
  await user.type(screen.getByLabelText('Новая задача'), '   ');
  await user.click(screen.getByRole('button', { name: 'Добавить' }));

  // Assert
  expect(screen.getByText('Задач нет')).toBeInTheDocument();
});
```

**Изоляция тестов:**

*   Каждый тест должен быть **независимым**: результат не зависит от порядка запуска и от других тестов.
*   Общая настройка выносится в `beforeEach`, очистка — в `afterEach`.
*   Моки сбрасывайте между тестами: `vi.clearAllMocks()` или `mockedFn.mockReset()`.
*   React Testing Library автоматически размонтирует компонент после каждого теста, если доступны глобальные `afterEach` (включён `globals: true`).

```ts
beforeEach(() => {
  vi.clearAllMocks();
  localStorage.clear();
});
```

**Что не нужно тестировать:**

| Не тестируйте | Почему |
|---------------|--------|
| Внутреннее состояние и приватные методы компонента | Это детали реализации; они меняются при рефакторинге |
| CSS-классы и точную структуру DOM | Тест станет хрупким и будет падать при смене вёрстки |
| Сторонние библиотеки (React, router, UI-kit) | Их уже протестировали авторы |
| Геттеры/сеттеры и тривиальный код | Тест не приносит ценности |
| Автоматические снапшоты «всего компонента» | Большие снапшоты непонятны и легко «перезаписываются» без анализа |

Лучше сосредоточиться на **пользовательских сценариях**, **граничных случаях** (пустой список, ошибка, максимальное значение) и **негативных сценариях** (неверный ввод, отказ сервера).

### **Матчеры jest-dom: шпаргалка**

После подключения `@testing-library/jest-dom/vitest` становятся доступны удобные матчеры:

| Матчер | Проверяет |
|--------|-----------|
| `toBeInTheDocument()` | Элемент присутствует в DOM |
| `toBeVisible()` | Элемент видим |
| `toHaveTextContent('…')` | Текстовое содержимое |
| `toHaveValue('…')` | Значение поля ввода |
| `toBeDisabled()` / `toBeEnabled()` | Доступность элемента |
| `toBeChecked()` | Отмеченный чекбокс/радио |
| `toHaveClass('…')` | CSS-класс |
| `toHaveAttribute('href', '…')` | Атрибут |
| `toBeEmptyDOMElement()` | Элемент пуст |

### **Резюме**

*   **Тесты** ускоряют разработку и делают рефакторинг безопасным. Основание пирамиды — быстрые и дешёвые **unit-тесты**.
*   **Vitest** — нативный для Vite тест-раннер с API, совместимым с Jest. Настраивается в `vite.config.ts` (секция `test`), матчеры подключаются в `src/test/setup.ts`.
*   **React Testing Library** пропагандирует тестирование **поведения пользователя**: поиск по роли, подписи и тексту, взаимодействие через `user-event`, проверка видимого результата.
*   **Запросы** делятся по приоритету (`getByRole` — лучший, `getByTestId` — крайний случай) и по варианту (`getBy` / `queryBy` / `findBy`).
*   **Взаимодействие** лучше имитировать через `userEvent.setup()` и `await`-методы; **асинхронность** проверяется через `findBy*` и `waitFor`.
*   **Моки** (`vi.fn`, `vi.mock`, `vi.spyOn`) изолируют компонент от сети и внешних зависимостей; кастомные хуки тестируются через `renderHook`.
*   Тесты пишутся по паттерну **Arrange — Act — Assert**, должны быть независимыми и не проверять детали реализации.
