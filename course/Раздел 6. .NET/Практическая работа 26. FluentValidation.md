# Практическая работа 26. FluentValidation

## Тема
Валидация входных данных в ASP.NET Core Web API с помощью библиотеки FluentValidation

## Цель
Изучить назначение и преимущества валидации входных данных, освоить построение валидаторов на основе `AbstractValidator<T>`, настроить регистрацию валидаторов в контейнере зависимостей и научиться возвращать клиенту понятные сообщения об ошибках в формате `ValidationProblemDetails`.

## Теоретическая часть

### Зачем нужна валидация

Любые данные, приходящие извне (тело запроса, строка запроса, маршрут), нельзя считать доверенными. Валидация решает сразу несколько задач:

- **Безопасность.** Отсекает некорректные и потенциально опасные данные до того, как они попадут в бизнес-логику или базу данных.
- **Целостность данных.** Не позволяет сохранить сущность, нарушающую правила предметной области (пустое имя, отрицательная цена, некорректный email).
- **Качество API.** Клиент получает не «500 Internal Server Error», а понятный ответ `400 Bad Request` с перечнем конкретных ошибок по полям.
- **Разделение ответственности.** Правила валидации живут отдельно от контроллеров и сервисов, не засоряя их код десятками проверок `if`.

> **Важно.** Валидация — это не замена бизнес-правилам. Она проверяет *форму* данных (заполнено ли поле, не превышена ли длина, корректен ли формат), тогда как бизнес-правила (например, «нельзя снять больше, чем есть на счёте») реализуются в сервисном слое.

### DataAnnotations и FluentValidation

.NET «из коробки» предоставляет атрибуты `System.ComponentModel.DataAnnotations`: `[Required]`, `[StringLength]`, `[Range]`, `[EmailAddress]`. Их просто применять, но у них есть ограничения.

| Критерий | DataAnnotations | FluentValidation |
|---|---|---|
| Где описываются правила | Атрибутами прямо на модели | В отдельном классе-валидаторе |
| Условные правила (`When`) | Сложно | Легко и читаемо |
| Кросс-полевые проверки | Через `IValidatableObject` | Через `Must`, `When`, доступ к другим полям |
| Сообщения об ошибках | `ErrorMessage` в атрибуте | `WithMessage`, локализация, динамические сообщения |
| Тестирование | Затруднено | Легко (валидатор — обычный класс) |
| Вложенные объекты и коллекции | Ограниченно | `SetValidator`, `RuleForEach` |
| Разделение моделей API и правил | Правила «приклеены» к DTO | Полное разделение слоёв |

Вывод: для небольших моделей достаточно DataAnnotations, но в реальных проектах FluentValidation даёт больше гибкости, лучше тестируется и не смешивает транспортную модель с логикой проверки.

### Установка пакетов

В проекте ASP.NET Core Web API (.NET 8) необходимо установить два пакета:

```bash
dotnet add package FluentValidation.AspNetCore
dotnet add package FluentValidation.DependencyInjectionExtensions
```

- `FluentValidation.AspNetCore` — интеграция с ASP.NET Core: автоматическая валидация моделей `[ApiController]`, клиентские адаптеры.
- `FluentValidation.DependencyInjectionExtensions` — метод расширения `AddValidatorsFromAssemblyContaining<T>()` для регистрации всех валидаторов сборки в DI.

> **Совет.** Версии пакетов должны совпадать (например, обе `11.x`), иначе возможны конфликты сборок.

### Класс валидатора: `AbstractValidator<T>`

Валидатор — обычный класс, наследующий `AbstractValidator<T>`, где `T` — тип проверяемой модели. Правила задаются в конструкторе через методы `RuleFor`.

```csharp
using FluentValidation;

public class CreateProductRequestValidator : AbstractValidator<CreateProductRequest>
{
    public CreateProductRequestValidator()
    {
        RuleFor(x => x.Name)
            .NotEmpty().WithMessage("Название товара обязательно для заполнения.")
            .MaximumLength(100).WithMessage("Название не должно превышать 100 символов.");
    }
}
```

Правила применяются в том порядке, в котором объявлены. По умолчанию сбой одного правила не мешает выполнению следующих. Это поведение управляется **каскадным режимом** (`CascadeMode`).

### Основные правила

| Правило | Назначение |
|---|---|
| `NotNull()` | Значение не равно `null` |
| `NotEmpty()` | Строка не пуста и не состоит из пробелов; коллекция не пуста; число не равно `0` |
| `MinimumLength(n)` | Минимальная длина строки |
| `MaximumLength(n)` | Максимальная длина строки |
| `Length(min, max)` | Длина в диапазоне |
| `EmailAddress()` | Корректный адрес электронной почты |
| `Matches(regex)` | Соответствие регулярному выражению |
| `GreaterThan(value)` / `GreaterThanOrEqualTo(value)` | Число больше (или равно) значения |
| `LessThan(value)` / `LessThanOrEqualTo(value)` | Число меньше (или равно) значения |
| `InclusiveBetween(from, to)` | Число в диапазоне включительно |
| `Must(predicate)` | Произвольная проверка-предикат |
| `When(predicate, action)` | Условное применение вложенных правил |
| `RuleForEach(x => x.Collection)` | Применение правил к каждому элементу коллекции |
| `SetValidator(...)` | Вложенный валидатор для свойства-объекта |
| `WithMessage(...)` | Текст сообщения об ошибке |
| `WithName(...)` | Отображаемое имя поля в сообщении |

### Примеры правил

```csharp
public class CreateProductRequestValidator : AbstractValidator<CreateProductRequest>
{
    public CreateProductRequestValidator()
    {
        // Обязательное поле и ограничение длины
        RuleFor(x => x.Name)
            .NotEmpty().WithMessage("Название обязательно.")
            .MaximumLength(100).WithMessage("Не более 100 символов.");

        RuleFor(x => x.Description)
            .MinimumLength(10).WithMessage("Описание не короче 10 символов.")
            .MaximumLength(1000).WithMessage("Описание не длиннее 1000 символов.");

        // Числовое условие
        RuleFor(x => x.Price)
            .GreaterThan(0).WithMessage("Цена должна быть больше 0.")
            .LessThanOrEqualTo(1_000_000).WithMessage("Цена слишком велика.");

        // Артикул по шаблону
        RuleFor(x => x.Sku)
            .Matches("^[A-Z0-9-]{4,20}$").WithMessage("Артикул: 4–20 символов A–Z, 0–9 и дефис.");

        // Условное правило: скидка проверяется, только если она объявлена
        RuleFor(x => x.Discount)
            .GreaterThan(0).WithMessage("Скидка должна быть больше 0.")
            .LessThan(x => x.Price).WithMessage("Скидка не может превышать цену.")
            .When(x => x.HasDiscount);

        // Произвольная проверка через Must
        RuleFor(x => x.Price)
            .Must(price => price % 0.01m == 0)
            .WithMessage("Цена должна быть кратна 1 копейке.");

        // Правила для каждого элемента коллекции
        RuleForEach(x => x.Tags)
            .NotEmpty().WithMessage("Тег не может быть пустым.")
            .MaximumLength(30).WithMessage("Тег не длиннее 30 символов.");
    }
}
```

### Каскадные режимы

Каскадный режим определяет, продолжать ли проверку поля после первой ошибки.

- `CascadeMode.Continue` (по умолчанию) — выполняются все правила, клиент видит все ошибки поля сразу. Удобно для UX.
- `CascadeMode.Stop` — после первой ошибки остальные правила поля не выполняются. Удобно, когда последующие правила зависят от предыдущих (например, нельзя проверять длину `null`-строки).

```csharp
// Каскад для одного правила
RuleFor(x => x.Name)
    .Cascade(CascadeMode.Stop)
    .NotNull().WithMessage("Название обязательно.")
    .NotEmpty().WithMessage("Название не может быть пустым.")
    .MaximumLength(100).WithMessage("Не более 100 символов.");
```

```csharp
// Глобальная настройка (например, в Program.cs до построения приложения)
ValidatorOptions.Global.DefaultClassLevelCascadeMode = CascadeMode.Stop;
```

### Кастомные сообщения на русском

Для каждого правила можно задать своё сообщение через `WithMessage`. В сообщениях доступны плейсхолдеры `{PropertyName}`, `{PropertyValue}`, `{MinLength}`, `{MaxLength}` и другие.

```csharp
RuleFor(x => x.Email)
    .NotEmpty().WithMessage("Электронная почта обязательна для заполнения.")
    .EmailAddress().WithMessage("Адрес «{PropertyValue}» имеет неверный формат.")
    .WithName("Электронная почта");
```

> **Совет.** Не дублируйте название поля в тексте — используйте `WithName`, тогда `{PropertyName}` подставит понятное пользователю имя.

Для сложных случаев переопределяют `PropertyName` через `.OverridePropertyName("...")`, а вложенные имена формируются через `RuleFor(x => x.Address.City)`.

### Регистрация валидаторов в DI

Все валидаторы сборки регистрируются одним вызовом:

```csharp
builder.Services.AddValidatorsFromAssemblyContaining<Program>();
```

Метод сканирует сборку, находит все классы-наследники `AbstractValidator<T>` и регистрирует их как `IValidator<T>`. После этого валидатор можно запрашивать через конструктор:

```csharp
public class ProductsController(IValidator<CreateProductRequest> validator) : ControllerBase { }
```

### Интеграция: автоматическая и ручная валидация

**Автоматическая валидация** включается одним вызовом. При этом для контроллеров с атрибутом `[ApiController]` модель проверяется до входа в action; при ошибке автоматически возвращается `400 Bad Request` в формате `ValidationProblemDetails`, и метод контроллера не выполняется.

```csharp
builder.Services.AddFluentValidationAutoValidation();
```

**Ручная валидация** даёт полный контроль: валидатор вызывается явно через `IValidator<T>.ValidateAsync`, и разработчик сам решает, как и когда вернуть ошибки. Это полезно, когда нужна нестандартная логика (например, объединить ошибки валидации с проверками в сервисе).

```csharp
var result = await validator.ValidateAsync(request, ct);
if (!result.IsValid)
{
    foreach (var failure in result.Errors)
        ModelState.AddModelError(failure.PropertyName, failure.ErrorMessage);

    return ValidationProblem(ModelState);
}
```

> **Примечание.** При включённой автоматической валидации ручная проверка становится избыточной для большинства action-методов, но пригодится в Minimal API, фоновых сервисах и при сложной композиции проверок.

### Формат ответа с ошибками

ASP.NET Core возвращает ошибки валидации в формате `ValidationProblemDetails` (разновидность RFC 7807 `ProblemDetails`):

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": ["Название товара обязательно для заполнения."],
    "Price": ["Цена должна быть больше 0."]
  },
  "traceId": "00-8f3a...-01"
}
```

Поле `errors` — словарь «имя поля → массив сообщений». Такой формат легко обрабатывается любым HTTP-клиентом.

## Ход работы

1. Создать проект ASP.NET Core Web API (.NET 8) командой `dotnet new webapi -n ProductValidationApi` и открыть его в Visual Studio (или VS Code).
2. Установить пакеты `FluentValidation.AspNetCore` и `FluentValidation.DependencyInjectionExtensions`.
3. Создать DTO запроса (`CreateProductRequest`) и модель ответа (`Product`) для выбранного варианта задания.
4. Реализовать валидатор `CreateProductRequestValidator : AbstractValidator<CreateProductRequest>` со всеми правилами варианта, сообщениями на русском и каскадным режимом там, где это нужно.
5. Зарегистрировать валидаторы в DI (`AddValidatorsFromAssemblyContaining<Program>()`) и настроить валидацию моделей.
6. Реализовать контроллер с POST-методом: либо полагаться на автоматическую валидацию, либо вызвать `IValidator<T>.ValidateAsync` вручную и вернуть `ValidationProblem(ModelState)`.
7. Запустить проект, через Swagger отправить корректный и некорректный запросы, зафиксировать успешный ответ `201` и ответ `400` с ошибками.
8. Сделать скриншоты, оформить `README.md` и загрузить решение в репозиторий Gogs.

### 2. Валидатор

```csharp
// Validators/CreateProductRequestValidator.cs
using FluentValidation;
using ProductValidationApi.Dtos;

namespace ProductValidationApi.Validators;

/// <summary>
/// Валидатор запроса на создание товара.
/// </summary>
public class CreateProductRequestValidator : AbstractValidator<CreateProductRequest>
{
    public CreateProductRequestValidator()
    {
        // Название: обязательно, ограничение длины, каскад
        RuleFor(x => x.Name)
            .Cascade(CascadeMode.Stop)
            .NotEmpty().WithMessage("Название товара обязательно для заполнения.")
            .MaximumLength(100).WithMessage("Название не должно превышать 100 символов.")
            .WithName("Название");

        // Описание: от 10 до 1000 символов
        RuleFor(x => x.Description)
            .MinimumLength(10).WithMessage("Описание должно содержать не менее 10 символов.")
            .MaximumLength(1000).WithMessage("Описание не должно превышать 1000 символов.");

        // Артикул: шаблон
        RuleFor(x => x.Sku)
            .NotEmpty().WithMessage("Артикул обязателен для заполнения.")
            .Matches("^[A-Z0-9-]{4,20}$")
            .WithMessage("Артикул должен содержать от 4 до 20 символов A–Z, 0–9 и дефис.")
            .WithName("Артикул");

        // Цена: положительная и разумная
        RuleFor(x => x.Price)
            .GreaterThan(0).WithMessage("Цена должна быть больше 0.")
            .LessThanOrEqualTo(1_000_000).WithMessage("Цена не может превышать 1 000 000 рублей.");

        // Категория: обязательна
        RuleFor(x => x.Category)
            .NotEmpty().WithMessage("Категория обязательна для заполнения.")
            .MaximumLength(50).WithMessage("Категория не должна превышать 50 символов.");

        // Скидка проверяется только при HasDiscount = true
        RuleFor(x => x.Discount)
            .GreaterThan(0).WithMessage("Размер скидки должен быть больше 0.")
            .LessThan(x => x.Price).WithMessage("Скидка не может быть больше или равна цене.")
            .When(x => x.HasDiscount);

        // Проверка каждого тега
        RuleForEach(x => x.Tags)
            .NotEmpty().WithMessage("Тег не может быть пустым.")
            .MaximumLength(30).WithMessage("Тег не должен превышать 30 символов.");

        // Вложенный объект
        RuleFor(x => x.Warehouse)
            .NotNull().WithMessage("Адрес склада обязателен.")
            .SetValidator(new WarehouseAddressRequestValidator());
    }
}

/// <summary>
/// Валидатор адреса склада.
/// </summary>
public class WarehouseAddressRequestValidator : AbstractValidator<WarehouseAddressRequest>
{
    public WarehouseAddressRequestValidator()
    {
        RuleFor(x => x.City)
            .NotEmpty().WithMessage("Город обязателен для заполнения.")
            .MaximumLength(60).WithMessage("Название города не должно превышать 60 символов.");

        RuleFor(x => x.Street)
            .NotEmpty().WithMessage("Улица обязательна для заполнения.")
            .MaximumLength(120).WithMessage("Адрес не должен превышать 120 символов.");
    }
}
```

### 4. Контроллер с ручной проверкой валидатора

```csharp
// Controllers/ProductsController.cs
using FluentValidation;
using Microsoft.AspNetCore.Mvc;
using ProductValidationApi.Dtos;
using ProductValidationApi.Models;

namespace ProductValidationApi.Controllers;

/// <summary>
/// Операции над товарами.
/// </summary>
[ApiController]
[Route("api/[controller]")]
public class ProductsController(IValidator<CreateProductRequest> validator) : ControllerBase
{
    // Хранилище в памяти для примера
    private static readonly List<Product> Products = new();
    private static int _nextId = 1;

    /// <summary>
    /// Создать новый товар.
    /// </summary>
    [HttpPost]
    [ProducesResponseType(typeof(Product), StatusCodes.Status201Created)]
    [ProducesResponseType(typeof(ValidationProblemDetails), StatusCodes.Status400BadRequest)]
    public async Task<IActionResult> Create(
        [FromBody] CreateProductRequest request,
        CancellationToken ct)
    {
        // При включённой автоматической валидации [ApiController] вернёт 400
        // до входа в метод. Ручной вызов показан для полноты и контроля:
        var validationResult = await validator.ValidateAsync(request, ct);
        if (!validationResult.IsValid)
        {
            foreach (var failure in validationResult.Errors)
            {
                ModelState.AddModelError(failure.PropertyName, failure.ErrorMessage);
            }

            return ValidationProblem(ModelState);
        }

        var product = new Product
        {
            Id = _nextId++,
            Name = request.Name,
            Description = request.Description,
            Sku = request.Sku,
            Price = request.Price,
            Category = request.Category
        };

        Products.Add(product);

        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);
    }

    /// <summary>
    /// Получить товар по идентификатору.
    /// </summary>
    [HttpGet("{id:int}")]
    [ProducesResponseType(typeof(Product), StatusCodes.Status200OK)]
    [ProducesResponseType(StatusCodes.Status404NotFound)]
    public IActionResult GetById(int id)
    {
        var product = Products.FirstOrDefault(p => p.Id == id);
        return product is null ? NotFound() : Ok(product);
    }
}
```


### 5. Пример ответа 400 при некорректных данных

Запрос:

```json
{
  "name": "",
  "description": "Коротко",
  "sku": "abc",
  "price": -5,
  "category": "",
  "hasDiscount": true,
  "discount": 100,
  "tags": [""],
  "warehouse": { "city": "", "street": "" }
}
```

Ответ `400 Bad Request`:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": ["Название товара обязательно для заполнения."],
    "Description": ["Описание должно содержать не менее 10 символов."],
    "Sku": ["Артикул должен содержать от 4 до 20 символов A–Z, 0–9 и дефис."],
    "Price": ["Цена должна быть больше 0."],
    "Category": ["Категория обязательна для заполнения."],
    "Discount": ["Скидка не может быть больше или равна цене."],
    "Tags[0]": ["Тег не может быть пустым."],
    "Warehouse.City": ["Город обязателен для заполнения."],
    "Warehouse.Street": ["Улица обязательна для заполнения."]
  },
  "traceId": "00-1c2d3e4f5a6b7c8d9e0f-1122334455667788-01"
}
```

> **Обратите внимание.** Ошибки вложенных объектов приходят с составными именами (`Warehouse.City`), а ошибки элементов коллекций — с индексами (`Tags[0]`). Это упрощает подсветку полей на клиенте.

## 15 вариантов заданий

Для каждого варианта требуется создать DTO запроса, валидатор `AbstractValidator<T>` и POST-endpoint, возвращающий `400` с сообщениями на русском при некорректных данных.

**Вариант 1: Регистрация пользователя**
Поля: `Login`, `Email`, `Password`, `ConfirmPassword`, `Age`, `Phone`.
Правила: логин 3–20 символов только латиница/цифры; корректный email; пароль не короче 8 символов; пароль и подтверждение совпадают (кросс-полевое правило через `Must`); возраст 14–100; телефон в формате `+7...` через `Matches`.

**Вариант 2: Оформление заказа**
Поля: `CustomerName`, `ProductId`, `Quantity`, `Address`, `DeliveryDate`, `PromoCode`.
Правила: имя обязательно; `ProductId > 0`; количество 1–1000; адрес не короче 10 символов; дата доставки — не в прошлом (`Must`); промокод проверяется по шаблону только при `UsePromoCode = true`.

**Вариант 3: Книга в библиотеке**
Поля: `Title`, `Author`, `ISBN`, `Year`, `Pages`, `Genre`.
Правила: название и автор обязательны; ISBN по шаблону `^978-\d{1,5}-\d{1,7}-\d{1,6}-\d$`; год 1450–текущий; страниц 1–5000; жанр из ограниченного списка (`Must`).

**Вариант 4: Регистрация студента**
Поля: `FirstName`, `LastName`, `Email`, `Phone`, `BirthDate`, `GroupNumber`.
Правила: имя и фамилия только буквы, 2–50 символов; email корректный; телефон по `Matches`; дата рождения — возраст не менее 15 лет; номер группы по шаблону `^[А-Я]{2}-\d{2}-\d$`.

**Вариант 5: Создание события**
Поля: `Title`, `Description`, `StartDate`, `EndDate`, `Location`, `MaxParticipants`.
Правила: название обязательно; описание ≤ 2000 символов; дата начала не в прошлом; дата окончания позже даты начала (кросс-полевое правило); место обязательно; число участников 1–10 000.

**Вариант 6: Добавление товара**
Поля: `Name`, `Price`, `Quantity`, `Category`, `SupplierEmail`.
Правила: название 3–100 символов; цена > 0 и ≤ 1 000 000; количество ≥ 0; категория из списка; email поставщика корректен.

**Вариант 7: Отзыв о товаре**
Поля: `ProductId`, `Author`, `Rating`, `Comment`, `Pros`, `Cons`.
Правила: `ProductId > 0`; имя автора обязательно; рейтинг — целое от 1 до 5; комментарий 10–2000 символов; списки «плюсы» и «минусы» проверяются через `RuleForEach` (каждый пункт ≤ 100 символов).

**Вариант 8: Платёж**
Поля: `AccountNumber`, `Amount`, `Currency`, `PaymentDate`, `Purpose`.
Правила: счёт по шаблону из 20 цифр; сумма > 0 и ≤ 10 000 000; валюта одна из `RUB`, `USD`, `EUR`; дата не в будущем; назначение обязательно, ≤ 200 символов.

**Вариант 9: Бронирование**
Поля: `ResourceName`, `GuestCount`, `StartTime`, `EndTime`, `ContactPhone`.
Правила: ресурс обязателен; число гостей 1–50; время окончания позже времени начала; длительность ≤ 8 часов (`Must`); телефон по шаблону.

**Вариант 10: Сотрудник**
Поля: `FullName`, `Position`, `Salary`, `HireDate`, `Email`, `Department`.
Правила: ФИО обязательно; должность 2–60 символов; оклад ≥ минимального (например, 20 000); дата приёма не в будущем; email корпоративный (`Must` — оканчивается на домен компании); подразделение из списка.

**Вариант 11: Курс**
Поля: `Title`, `Instructor`, `DurationHours`, `Price`, `StartDate`, `MaxStudents`.
Правила: название 5–120 символов; преподаватель обязателен; длительность 1–500 часов; цена ≥ 0; дата старта не в прошлом; число студентов 1–500.

**Вариант 12: Комментарий**
Поля: `PostId`, `AuthorName`, `Text`, `ParentCommentId`.
Правила: `PostId > 0`; имя 2–50 символов; текст 1–1000 символов; `ParentCommentId` — либо `null`, либо > 0 (условное правило через `When`).

**Вариант 13: Адрес доставки**
Поля: `Country`, `City`, `Street`, `House`, `Apartment`, `PostalCode`, `RecipientPhone`.
Правила: страна и город обязательны; улица 3–120 символов; дом обязателен; квартира — 1–10000 при наличии; индекс по шаблону из 6 цифр; телефон по шаблону.

**Вариант 14: Задача**
Поля: `Title`, `Description`, `Priority`, `DueDate`, `AssigneeEmail`, `EstimatedHours`.
Правила: название 3–150 символов; описание ≤ 2000; приоритет из `Low`, `Medium`, `High`, `Critical`; срок не в прошлом; email исполнителя корректный (только если назначен); оценка 0.5–100 часов.

**Вариант 15: Абитуриент**
Поля: `FullName`, `BirthDate`, `PassportSeries`, `PassportNumber`, `Specialty`, `AverageScore`, `Email`.
Правила: ФИО только буквы; возраст ≥ 14; серия — 4 цифры; номер — 6 цифр; специальность из списка; средний балл 2.0–5.0; email корректный.

## Критерии оценки

### 5 (Отлично)
- Все поля DTO снабжены корректными правилами FluentValidation
- Сообщения об ошибках на русском, понятны пользователю
- Использованы условные правила (`When`) и/или правила для коллекций (`RuleForEach`) там, где это требуется вариантом
- Валидаторы зарегистрированы в DI, endpoint возвращает `ValidationProblemDetails` со статусом `400`
- Код компилируется и работает, `dotnet build` проходит без ошибок
- README.md оформлен, приложены скриншоты успешного и ошибочного ответов

### 4 (Хорошо)
- Реализованы основные правила валидации
- Есть незначительные недочёты (отсутствуют условные правила, часть сообщений на английском)
- API работает, но не все граничные случаи проверены
- README.md оформлен с небольшими недочётами

### 3 (Удовлетворительно)
- Реализована только базовая валидация (обязательность и длина строк)
- Не настроена регистрация валидаторов в DI
- Ошибки возвращаются в нестандартном формате
- README.md оформлен не полностью

### 2 (Неудовлетворительно)
- Валидация отсутствует или не работает
- Проект не компилируется
- Отсутствует README.md или он оформлен небрежно

## Инструкция по сдаче работы

1. Создать репозиторий на локальном Gogs-сервере: `http://192.168.4.90/`.
2. Клонировать репозиторий локально.
3. Создать проект ASP.NET Core Web API (.NET 8) в папке репозитория:
   ```bash
   dotnet new webapi -n ProductValidationApi
   cd ProductValidationApi
   ```
4. Установить пакеты валидации:
   ```bash
   dotnet add package FluentValidation.AspNetCore
   dotnet add package FluentValidation.DependencyInjectionExtensions
   ```
5. Реализовать DTO, валидатор и контроллер согласно варианту задания.
6. Проверить сборку и запуск: `dotnet build`, затем `dotnet run`; протестировать endpoint через Swagger UI.
7. Убедиться, что при некорректных данных возвращается `400` с сообщениями на русском.
8. Сделать скриншоты успешного ответа и ответа с ошибками, поместить их в папку `assets/images`.
9. Оформить `README.md` с описанием задания, реализацией, командами запуска и скриншотами.
10. Запушить изменения в Gogs (`git add .`, `git commit -m "Практическая работа 26. FluentValidation"`, `git push`) и предоставить ссылку на репозиторий преподавателю.
